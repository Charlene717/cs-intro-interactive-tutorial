Codd 的 12 頁論文

1970：Codd 的 12 頁論文

1970 年 6 月，IBM 聖荷西實驗室的數學家 Edgar F. Codd 在 ACM 期刊發表一篇 12 頁的論文：《A Relational Model of Data for Large Shared Data Banks》。論文主張：資料應該以「關聯 (relation, 即表格)」表達，使用者只需描述「要什麼」(declarative)，不必管「怎麼拿」——這套關聯模型後來變成 SQL 的數學基礎。

但 IBM 的高層當時並不在意——他們在賣自家的 IMS (Information Management System)，層級式資料庫已賺進大錢，不想自打嘴巴。Codd 為此抗議多年。1977 年，一位前 IBM 員工 Larry Ellison 在加州 Redwood 創辦了一家叫 Software Development Laboratories 的公司，讀完 Codd 的論文後決定搶在 IBM 之前商業化關聯式資料庫。1979 年他們發布 Oracle V2，把對手 IBM DB2 整整甩開 4 年。今天 Oracle 市值 4500 億美元；Larry Ellison 是世界最富的人之一——全部建立在 IBM 自己當年不重視的論文上。

2026 年的今天：① 關聯式 DB（PostgreSQL、MySQL、Oracle、SQL Server）仍是企業資料的基石；② NoSQL（MongoDB、Redis、Cassandra）填補大規模分散式需求；③ 向量資料庫（Pinecone、Milvus、Weaviate、pgvector）因為 RAG 與 AI 興起一夕爆紅。本章帶你看：SQL 50 年來為何打不倒？NoSQL 為何叫「Not Only SQL」？scRNA-seq embedding 在向量 DB 怎麼跑 KNN？

June 1970 — IBM San Jose mathematician Edgar F. Codd published a 12-page paper in ACM: "A Relational Model of Data for Large Shared Data Banks." It argued that data should be represented as relations (tables); users state what they want (declarative), not how to fetch it. This relational model became SQL's mathematical foundation.

But IBM brass didn't care — they were selling their hierarchical IMS database, raking in cash, and didn't want to cannibalize themselves. Codd protested for years. In 1977, ex-IBM engineer Larry Ellison founded Software Development Laboratories in Redwood, CA. After reading Codd's paper, he decided to beat IBM to market with a relational DB. Oracle V2 shipped in 1979 — four years ahead of IBM DB2. Today Oracle is worth USD 450B; Ellison is one of the richest people alive — built entirely on IBM's own ignored paper.

2026 today: (1) relational DBs (PostgreSQL, MySQL, Oracle, SQL Server) still anchor enterprise data; (2) NoSQL (MongoDB, Redis, Cassandra) fills distributed-scale needs; (3) vector DBs (Pinecone, Milvus, Weaviate, pgvector) exploded with RAG/AI. This chapter: why hasn't SQL died in 50 years? Why is NoSQL really "Not Only SQL"? How do scRNA-seq embeddings run KNN in a vector DB?

💡
核心觀念：資料庫的根本價值不在「存資料」（檔案系統就能存）——而在於並行控制 (concurrency)、事務 (transactions)、查詢優化 (query optimization) 與持久性 (durability)。沒有 DB，1000 個使用者同時改一份 Excel 會立刻打架。 Core idea: A database's fundamental value isn't "storing data" (a filesystem does that) — it's concurrency control, transactions, query optimization, and durability. Without a DB, 1000 users editing one Excel file would deadlock instantly.

一、核心概念：六大資料庫家族

2026 年的資料庫世界可分成六大家族，每家有不同的存取模式、規模假設與一致性權衡：

The 2026 database world has six families, each with different access patterns, scale assumptions, and consistency trade-offs:

📊

① RDBMS（關聯式）

代表：PostgreSQL、MySQL、Oracle、SQL Server、SQLite。
資料模型：表格 + 外鍵；ACID 保證；SQL 查詢。
適用：金融、ERP、訂單系統、生物醫學登記資料庫。佔企業資料庫 70%+。

Examples: PostgreSQL, MySQL, Oracle, SQL Server, SQLite.
Model: Tables + foreign keys; ACID; SQL.
Best for: Finance, ERP, orders, biomedical registries. 70%+ of enterprise DB market.

🔑

② Key-Value Store

代表：Redis、Memcached、DynamoDB、etcd。
資料模型：純粹的 key → value 對應；O(1) 查詢。
適用：session cache、即時排行榜、API rate limiting。記憶體優先（Redis 可達百萬 QPS）。

Examples: Redis, Memcached, DynamoDB, etcd.
Model: Pure key → value; O(1) lookups.
Best for: Session cache, leaderboards, API rate limiting. Memory-first (Redis hits 1M QPS).

📄

③ Document DB

代表：MongoDB、Couchbase、Firestore。
資料模型：JSON-like 文件，schema 彈性；嵌套結構。
適用：電子病歷 (EHR)、CMS 內容、產品目錄、IoT 半結構化資料。

Examples: MongoDB, Couchbase, Firestore.
Model: JSON-like documents, flexible schema; nested.
Best for: EHR, CMS, product catalogs, IoT semi-structured data.

📚

④ Wide-Column

代表：Cassandra、ScyllaDB、HBase、Google Bigtable。
資料模型：稀疏的 row → column-family；水平擴展設計。
適用：時序資料、廣告點擊串流、Netflix 推薦快取。Cassandra 跑 PB 級毫無壓力。

Examples: Cassandra, ScyllaDB, HBase, Google Bigtable.
Model: Sparse row → column-family; horizontal-scale-first.
Best for: Time-series, ad clickstreams, Netflix recommendation cache. Cassandra handles PB scale easily.

🕸️

⑤ Graph DB

代表：Neo4j、ArangoDB、Amazon Neptune、TigerGraph。
資料模型：節點 + 邊；查詢用 Cypher / Gremlin。
適用：社群網路、推薦系統、欺詐偵測、生物 pathway（KEGG、Reactome）。

Examples: Neo4j, ArangoDB, Amazon Neptune, TigerGraph.
Model: Nodes + edges; queried via Cypher / Gremlin.
Best for: Social networks, recommendations, fraud detection, biological pathways (KEGG, Reactome).

🧠

⑥ Vector DB

代表：Pinecone、Milvus、Weaviate、Qdrant、pgvector（Postgres 外掛）。
資料模型：高維向量 (~768、~1536 維)；查詢 = ANN（近似最近鄰）。
適用：RAG（LLM 檢索）、語意搜尋、scRNA-seq embedding 比對、影像相似度搜尋。2024 後爆紅。

Examples: Pinecone, Milvus, Weaviate, Qdrant, pgvector (Postgres extension).
Model: High-dim vectors (~768, ~1536-d); queries = ANN (approx nearest neighbor).
Best for: RAG (LLM retrieval), semantic search, scRNA-seq embedding lookup, image similarity. Exploded after 2024.

正規化 / ACID / CAP / 索引

三、深入剖析

3.1 正規化

正規化 (normalization) 是把資料拆分成多張表以消除冗餘與更新異常：

  • 1NF (第一正規式)：每個欄位只存單一值（不可有 list）。
  • 2NF：在 1NF 基礎上，所有非主鍵欄位都必須完全依賴於主鍵（不能依賴主鍵的一部分）。
  • 3NF：在 2NF 基礎上，非主鍵欄位之間不能相互依賴（消除遞移依賴）。
  • BCNF (Boyce-Codd)：3NF 的加強版，幾乎所有教科書範例的「正確設計」。

反向操作 = 反正規化 (denormalization)：為了加速讀取，故意在多張表存重複資料。OLAP（資料倉儲）愛用——例如 GTEx 把 gene × tissue × sample 全部展平到一張寬表，查詢飛快但更新麻煩。OLTP（交易系統）追求正規化；OLAP（分析）追求反正規化。

Normalization splits data across tables to eliminate redundancy and update anomalies:

  • 1NF: each cell holds a single value (no lists).
  • 2NF: 1NF + all non-key columns depend on the whole primary key (no partial dependency).
  • 3NF: 2NF + no transitive dependency between non-key columns.
  • BCNF (Boyce-Codd): a stricter 3NF; "correct design" in most textbooks.

The inverse = denormalization: deliberately duplicate data across tables to speed up reads. Loved by OLAP (data warehouses) — e.g., GTEx flattens gene × tissue × sample into one wide table for fast queries (slow updates). OLTP wants normalization; OLAP wants denormalization.

Isolation levels（隔離級別）：從寬鬆到嚴格——Read Uncommitted（看到髒讀）→ Read Committed（PostgreSQL 預設）→ Repeatable Read（MySQL InnoDB 預設）→ Serializable（最嚴格，最慢）。隔離越強、並行越差，這是核心 trade-off。
Isolation levels: from loose to strict — Read Uncommitted (dirty reads visible) → Read Committed (PostgreSQL default) → Repeatable Read (MySQL InnoDB default) → Serializable (strictest, slowest). Stronger isolation = worse concurrency — the core trade-off.

3.3 CAP 定理

Eric Brewer 2000 年提出的 CAP 定理：分散式系統不可能同時滿足三者，只能擇二。

  • C (Consistency)：所有節點看到相同資料。
  • A (Availability)：每次請求都能得到回應（不一定是最新的）。
  • P (Partition tolerance)：網路斷掉時系統仍能運作。

因為網路必定會斷（光纖被挖、機房斷電），P 是必須的。所以實務上是「CP（如 MongoDB、HBase——斷網時拒絕回應保持一致）」vs「AP（如 Cassandra、DynamoDB——斷網時繼續回應但可能不一致）」。RDBMS 在單機環境是 CA，分散式環境通常變 CP。

Eric Brewer's 2000 CAP theorem: a distributed system can't satisfy all three — pick two.

  • C: all nodes see the same data.
  • A: every request gets a response (possibly stale).
  • P: tolerates network partitions.

Since networks will partition (fibers cut, racks lose power), P is mandatory. So the real choice is CP (MongoDB, HBase — refuse responses during partition to stay consistent) vs AP (Cassandra, DynamoDB — keep responding, possibly stale). Single-node RDBMS is CA; distributed RDBMS usually becomes CP.

四個經典時刻

四、四個經典故事

1970–79：Codd 被自家忽視

1970 年 Codd 在 IBM 內部已經有原型 System R，但 IBM 高層不想自己打自己的 IMS。1973 年 Codd 公開挑戰 IBM CEO，被冷處理。前 IBM 員工 Larry Ellison 在 1977 年成立 SDL（後改名 Oracle），1979 年發布 Oracle V2——比 IBM 自家的 DB2 (1983) 整整早 4 年。IBM 後來才被迫加入競賽。Codd 1981 年獲圖靈獎，IBM 才正式承認他的貢獻。教訓：「偉大論文未必是好商業」，從學術到產品有巨大鴻溝。

By 1970 Codd had a working System R prototype inside IBM, but executives didn't want to cannibalize IMS. In 1973 Codd publicly challenged the IBM CEO and was sidelined. Ex-IBM engineer Larry Ellison founded SDL (later Oracle) in 1977 and shipped Oracle V2 in 1979 — four years ahead of IBM's DB2 (1983). IBM had to scramble to catch up. Codd won the Turing Award in 1981 — IBM finally acknowledged him. Lesson: great papers don't make great products — academia to product is a huge gap.

2009：NoSQL 一詞誕生

2009 年 6 月 11 日，Last.fm 工程師 Johan Oskarsson 在舊金山辦了一個 meetup，主題是「分散式、開源、非關聯式資料庫」。為了在 Twitter 上發文方便，他用了 #NoSQL 這個 hashtag。沒想到這個臨時取的詞紅了，10 年內催生 200+ 個 NoSQL 產品。重點：「NoSQL」從來不是「No SQL」（拒絕 SQL）——是「Not Only SQL」（不只用 SQL）。Cassandra、MongoDB、Couchbase 後來都加上類 SQL 的查詢語言（CQL、MQL）。

June 11, 2009 — Last.fm engineer Johan Oskarsson organized a San Francisco meetup on "distributed, open-source, non-relational databases." For Twitter convenience he used the hashtag #NoSQL. The casual name stuck and spawned 200+ NoSQL products in a decade. Crucially, "NoSQL" was never "No SQL" — it's "Not Only SQL." Cassandra, MongoDB, Couchbase later added SQL-like languages (CQL, MQL).

2018：MongoDB 認輸了？

2009 年 MongoDB 出現時，主打「沒有 schema、沒有 ACID」——「資料庫應該很彈性」。批評者抨擊：「沒有 ACID 怎麼能叫資料庫？」。經過 9 年市場洗禮，2018 年 MongoDB 4.0 正式加入「multi-document ACID transactions」。NoSQL 陣營實質上回到了 RDBMS 的設計原則。教訓：當你拋棄一個成熟系統 50 年累積的功能時，10 年內你會把它們一一再發明回來。今天 MongoDB、Cassandra、DynamoDB 都支援事務、二級索引、JOIN-like 操作。

When MongoDB launched in 2009 it sold "no schema, no ACID" — "databases should be flexible." Critics retorted: "how can it be a DB without ACID?" Nine years later, MongoDB 4.0 (2018) added multi-document ACID transactions. NoSQL effectively returned to RDBMS principles. Lesson: when you throw away 50 years of mature system features, you'll reinvent them all within 10 years. Today MongoDB, Cassandra, DynamoDB all support transactions, secondary indexes, and JOIN-like operations.

2024：向量 DB 爆發

ChatGPT 2022 年底引爆 LLM 熱潮後，RAG (Retrieval-Augmented Generation) 成為主流架構：先把文件 embed 成向量、存在 vector DB、查詢時找最相似的 K 個丟給 LLM。Pinecone 從 2023 的 7.5 億美元估值飆到 2024 的 75 億；Weaviate、Milvus、Qdrant 也都拿到大筆募資。同時 Postgres 的 pgvector 外掛實作 IVFFlat 與 HNSW，讓「在現有 RDBMS 內做向量檢索」變得簡單——很多人質疑專屬 vector DB 是否需要存在。2025+ 的趨勢：向量功能融入主流 DB（PostgreSQL、SQLite、MongoDB Atlas）vs 高效能專屬 vector DB 兩條路線並行。

After ChatGPT (late 2022) sparked the LLM boom, RAG (Retrieval-Augmented Generation) became the dominant pattern: embed documents into vectors, store in a vector DB, retrieve top-K similar at query time. Pinecone went from a USD 750M valuation in 2023 to USD 7.5B in 2024; Weaviate, Milvus, Qdrant all raised heavily. Meanwhile, Postgres's pgvector extension implements IVFFlat and HNSW, making "vector search inside an existing RDBMS" simple — many wonder if dedicated vector DBs are still needed. 2025+ trend: two roads in parallel — vector features absorbed into mainstream DBs (PostgreSQL, SQLite, MongoDB Atlas) vs high-performance dedicated vector DBs.

給生物資訊學家

六、🧬 給生物資訊學家

🧬
① Ensembl / UCSC = MySQL

Ensembl 與 UCSC Genome Browser 後端都用 MySQL，存數十億筆基因/轉錄本/變異記錄。典型查詢：SELECT * FROM gene WHERE chr='chr1' AND start > 1000000 AND biotype='protein_coding'。為何 MySQL？因為基因組查詢本質是「範圍查詢 + JOIN」，正是 RDBMS + B-tree 索引強項。UCSC 提供 public MySQL（genome-mysql.soe.ucsc.edu）任何人可直接連線，bioinformatics 開放科學的好榜樣。

Ensembl and UCSC use MySQL as backend, storing billions of gene/transcript/variant records. Typical query: SELECT * FROM gene WHERE chr='chr1' AND start > 1000000 AND biotype='protein_coding'. Why MySQL? Genome queries are range + JOIN — perfect for RDBMS + B-tree. UCSC's public MySQL (genome-mysql.soe.ucsc.edu) is a great open-science example.

🧬
② cBioPortal 整合臨床與基因組

cBioPortal（MSK，33 萬樣本）整合 TCGA、GENIE、ICGC 的癌症基因組+臨床資料，後端 MySQL + Spring Boot。「TP53 突變的肺癌存活曲線」需要 JOIN mutations + clinical_data。RDBMS 在這場景無敵；NoSQL 要寫複雜 application-level JOIN。學 SQL 比學任何 NoSQL 重要 100 倍——TCGA、UK Biobank、All of Us 全是關聯式。

cBioPortal (MSK, 330k samples) integrates TCGA, GENIE, ICGC on MySQL + Spring Boot. "Survival of TP53-mutant lung cancers" needs JOIN mutations + clinical_data. RDBMS wins; NoSQL needs ugly application JOINs. Learn SQL — 100× more important than any NoSQL. TCGA, UK Biobank, All of Us — all relational.

🧬
③ Neo4j 與生物路徑

生物 pathway 本質是圖：基因→酶→反應→代謝物。用 RDBMS 表達需要 6 次 JOIN（「EGFR 下游 3 步內」），Cypher 一行：MATCH (g:Gene {symbol:'EGFR'})-[*1..3]->(t) RETURN t。KEGG、Reactome 內部用 graph 模型；STRING-DB 蛋白互動可匯入 Neo4j；scRNA-seq GRN 推論（SCENIC）輸出天然是圖。藥物 repurposing（找與疾病 graph-鄰近的藥物）也是 Neo4j 招牌應用。

Biological pathways are graphs: gene→enzyme→reaction→metabolite. RDBMS needs 6 JOINs ("3 steps downstream of EGFR"); Cypher: MATCH (g:Gene {symbol:'EGFR'})-[*1..3]->(t) RETURN t — one line. KEGG, Reactome use graph internally; STRING-DB imports to Neo4j; scRNA-seq GRN inference (SCENIC) outputs are graphs. Drug repurposing (find drugs graph-adjacent to disease) is a Neo4j signature.

🧬
④ 向量 DB 與單細胞

百萬細胞 scRNA-seq atlas 經 PCA/scVI/Geneformer 後，每細胞為 50–256 維向量。Reference mapping = 1M query × 1M-NN = 1 兆次距離計算。樸素方法不可能。Milvus/Pinecone/pgvector 用 HNSW 或 IVF 索引把 O(N) 降到 O(log N)——百萬細胞 KNN 從幾小時變幾秒。Scanpy/Seurat 2024 後加上向量 DB integration（SCimilarity、CellRefiner）。

A 1M-cell atlas after PCA/scVI/Geneformer = 50–256-d vectors. Reference mapping = 1M queries × 1M-NN = 1 trillion distance computes — naive is hopeless. Milvus/Pinecone/pgvector use HNSW or IVF to drop O(N) to O(log N) — million-cell KNN goes from hours to seconds. Scanpy/Seurat (2024+) integrate vector DBs via SCimilarity, CellRefiner.

🧬
⑤ MongoDB 與 EHR

EHR 是半結構化的代表：每病患結構不同。塞進關聯式 schema 會有 100+ 張表 + 大量 NULL。MongoDB 文件模型契合——每病患一個 document。FHIR（HL7 JSON 標準）天然 maps 到 MongoDB。Mayo Clinic、Mount Sinai 都這樣用。2018 後加上 ACID 可行。代價：cross-patient SQL JOIN 要靠 aggregation pipeline 補。

EHRs are semi-structured — each patient differs. Relational schema = 100+ tables with NULLs. MongoDB documents fit naturally — one doc per patient. FHIR (HL7 JSON) maps to MongoDB directly. Mayo Clinic, Mount Sinai use this. Post-2018 ACID makes it viable. Trade-off: cross-patient JOIN needs aggregation pipeline.

// Hash Join：建立 + 探測階段
function InnerJoin(R, S, key):
    hash = {}
    for r in R: hash[r[key]] = r            // build
    result = []
    for s in S:
        if s[key] in hash:
            result.append(merge(hash[s[key]], s))   // probe
    return result
    // O(|R|+|S|) vs nested-loop O(|R|×|S|)

// ACID transaction
function Transfer(from_acc, to_acc, amount):
    BeginTransaction()
    try:
        balance = SELECT balance FROM accounts WHERE id = from_acc
        if balance < amount: throw InsufficientFunds
        UPDATE accounts SET balance = balance - amount WHERE id = from_acc
        UPDATE accounts SET balance = balance + amount WHERE id = to_acc
        Commit()
    catch e:
        Rollback(); throw e

// HNSW vector search
function HnswSearch(query_vec, K):
    entry = top_layer.entry
    for layer in top ... bottom:
        entry = GreedySearch(layer, entry, query_vec)
    return TopK(bottom.neighbors_of(entry), K)
    // O(log N) vs brute-force O(N)
常見陷阱

九、常見誤解

❌ NoSQL = No SQL

真相：NoSQL = Not Only SQL。Cassandra 有 CQL、MongoDB 有 MQL、CouchDB 有 N1QL。2018 後 NoSQL 紛紛加上 ACID。

Truth: NoSQL = Not Only SQL. Cassandra has CQL, MongoDB has MQL, CouchDB has N1QL. Post-2018 NoSQLs added ACID.

❌ 索引越多越好

真相：每個 index 是額外 B-tree 副本，INSERT/UPDATE/DELETE 要同步更新。10 個 index 可能讓 INSERT 慢 5–10×。原則：只對真會被查詢的欄位建；OLTP 克制 / OLAP 放鬆。WHERE、JOIN ON、ORDER BY 欄位首選。

Truth: Each index = extra B-tree copy; INSERT/UPDATE/DELETE must update all. 10 indexes can slow INSERT 5–10×. Rule: index only what's actually queried; OLTP — minimize, OLAP — be generous. Prefer WHERE, JOIN ON, ORDER BY columns.

❌ MongoDB 比 SQL 快

真相：視場景而定。MongoDB 在「單一文件 get/put」可能快；OLAP benchmark（TPC-H）PostgreSQL/DuckDB 完勝。真正快的不是 NoSQL，而是「放棄 ACID + JOIN 換來的水平擴展性」。

Truth: It depends. MongoDB may win on single-doc get/put; PostgreSQL/DuckDB crush MongoDB on OLAP (TPC-H). What's fast isn't NoSQL — it's "horizontal scale bought by dropping ACID + JOIN."

❌ ORM 不必懂 SQL

真相：SQLAlchemy、Django ORM 產生的 SQL 常常次優。經典 N+1 問題：取 N 個訂單、每個查客戶 → 1+N queries 而非 1 個 JOIN。在 R dbplyr 一定要 show_query() 看翻譯結果。學會 SQL 比學任何 ORM 重要。

Truth: SQLAlchemy, Django ORM often emit suboptimal SQL. Classic N+1 problem: fetch N orders, then query customer for each → 1+N queries instead of one JOIN. In R dbplyr always show_query(). Learn SQL — beats any ORM.

💭 延伸思考

十、延伸思考

  1. 為何 SQL 50 年沒被取代？
    1974 IBM 的 SQL 至今主流。GraphQL 想取代 API 層；NoSQL 想取代——10 年後加回 SQL-like。SQL 頑強：① 聲明式（說 what，DB 負責 how）；② 嚴謹數學基礎（關聯代數）；③ 大學+業界正回饋。下個 50 年：自然語言查詢取代手寫 SQL？還是 SQL 變成 LLM 的「中間表示」？ IBM's 1974 SQL still dominates. GraphQL tried API layer; NoSQL added SQL-like back in 10 years. SQL is resilient: (1) declarative, (2) rigorous math, (3) academia+industry feedback. Next 50 years: will natural language replace hand-written SQL? Or will SQL be LLM's "intermediate representation"?
  2. Vector DB 併入 Postgres？
    2024 RAG 熱讓 Pinecone/Milvus 成獨角獸。但 Postgres pgvector 也飛快——中等規模直接加 HNSW 就夠。趨勢：① 主流 DB 都加向量功能 → 專屬 vector DB 像 ETL 一樣被吸收；② 超大規模（10 億+向量）仍需專屬系統。對 bioinformatics 1 億細胞 ×768 維 atlas 哪個合適？scale-out vs scale-up 經典難題。 2024's RAG boom made Pinecone/Milvus unicorns. But pgvector improved fast — mid-scale apps just add HNSW. Two paths: (1) mainstream DBs absorb vector features (dedicated vector DBs swallowed like ETL tools); (2) ultra-large (10B+ vectors) still needs dedicated. For 100M-cell × 768-d atlas — which? Classic scale-out vs scale-up.
