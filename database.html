資料庫系統

為什麼不能用 CSV？因為資料庫提供併發控制、ACID 交易、索引加速與查詢語言——從關聯式到 NoSQL 再到 2026 的向量資料庫。

Why not just use a CSV? Because databases offer concurrency, ACID transactions, indexes, and a query language — from relational to NoSQL to 2026's vector DBs.

概覽

為何需要資料庫？

把資料存成 CSV 或 JSON 看似簡單，但一旦遇到「1000 個使用者同時下單」就會崩潰：誰先讀寫？讀到一半當機怎辦？要查「過去 30 天台北的訂單」要全表掃描嗎？

資料庫管理系統 (DBMS) 為此而生，提供四大核心能力：

  • 併發 (Concurrency)：許多使用者同時讀寫不衝突
  • ACID 交易：要嘛全做、要嘛全不做
  • 查詢語言 (SQL)：用宣告式語法描述「想要什麼」，由引擎決定「怎麼拿」
  • 索引 (Index)：在百萬筆資料中以 ~µs 找到一筆

Storing data as CSV or JSON sounds simple — until 1000 users place orders concurrently and the file collapses: who wrote first? What if the process crashed mid-write? Does every "orders in Taipei in last 30 days" query scan the whole file?

A DBMS (Database Management System) solves this with four core capabilities:

  • Concurrency — many users read/write without conflict
  • ACID transactions — all-or-nothing
  • Query language (SQL) — declarative "what I want," engine decides "how to fetch"
  • Indexes — find one row among millions in microseconds
💡
核心觀念：資料庫是「結構化儲存 + 併發控制 + 查詢引擎」三位一體。沒這三項，就只是檔案。 Core idea: A database is the trinity of structured storage + concurrency control + query engine. Strip any of these and it's just a file.

關聯模型基礎

二、主鍵、外鍵與正規化

主鍵 (Primary Key, PK)：唯一識別一筆紀錄的欄位（如 student_id）。外鍵 (Foreign Key, FK)：指向另一表主鍵的欄位，建立關聯。

正規化 (Normalization) 減少冗餘與更新異常：

  • 1NF：每欄都是「原子值」，不允許重複群組或陣列。
  • 2NF：滿足 1NF，且非主鍵欄完全相依於整個主鍵（消除部分相依）。
  • 3NF：滿足 2NF，且非主鍵欄不可相依於其他非主鍵欄（消除遞移相依）。

反正規化 (Denormalization)：為了讀取效能故意冗餘——常見於資料倉儲與 OLAP。

A primary key (PK) uniquely identifies a row (e.g., student_id). A foreign key (FK) references a PK in another table, creating a relationship.

Normalization reduces redundancy and update anomalies:

  • 1NF — every column is an atomic value (no nested arrays/groups).
  • 2NF — 1NF + non-key columns fully depend on the whole PK (no partial dependency).
  • 3NF — 2NF + no non-key column depends on another non-key column (no transitive dependency).

Denormalization deliberately duplicates data for read speed — common in data warehouses / OLAP.

交易模型


四、ACID、BASE 與 CAP




ACID意涵



Atomicity交易內所有操作「全部成功或全部失敗」All ops in a transaction succeed or all fail


Consistency交易前後資料庫滿足所有約束（PK/FK、check）DB stays valid w.r.t. all constraints (PK/FK, check)


Isolation同時的多個交易彷彿依序執行（4 個隔離級別）Concurrent transactions behave as if serial (4 isolation levels)


Durability已 commit 的資料即使斷電也不會遺失Committed data survives crashes




BASE = Basically Available, Soft state, Eventually consistent。許多 NoSQL（如 DynamoDB、Cassandra）為了水平擴展犧牲嚴格一致性，採用「最終一致」。


CAP 定理 (Brewer 2000)：分散式系統最多只能同時滿足三項中的兩項：


    

  • Consistency（所有節點看到相同資料）
    • 

  • Availability（每次請求都得到回應）
    • 

  • Partition tolerance（網路分裂仍可運作）
    • 



網路分裂幾乎一定會發生，所以實務上是「C 或 A 二選一」：MongoDB、HBase 選 CP；Cassandra、DynamoDB 選 AP。


BASE = Basically Available, Soft state, Eventually consistent. Many NoSQL stores (DynamoDB, Cassandra) trade strict consistency for horizontal scale via eventual consistency.


CAP Theorem (Brewer 2000): a distributed system can pick at most two of three:


    

  • Consistency (all nodes see the same data)
    • 

  • Availability (every request gets a response)
    • 

  • Partition tolerance (works under network splits)
    • 



Network partitions are inevitable, so the real choice is C or A: MongoDB and HBase choose CP; Cassandra and DynamoDB choose AP.

五、索引




索引類型查詢適用



B-tree / B+treeO(log n)範圍查詢、排序（多數 RDBMS 預設）Range queries, sorts (RDBMS default)


HashO(1) avg精確等值查詢，不支援範圍Exact equality, no range


Inverted indexO(log n)全文搜尋（Elasticsearch、Lucene）Full-text search (Elasticsearch, Lucene)


BitmapO(n/64)低基數欄位（性別、布林）Low-cardinality columns


HNSW / IVF (向量)O(log n) ANN高維向量近鄰（RAG、語義搜尋）High-dim ANN (RAG, semantic search)




⚠️


索引不是免費的：每加一個索引，INSERT/UPDATE/DELETE 都得多維護一個結構。寫多讀少的表索引要少；讀多寫少的表（如報表、查詢）可以多。


Indexes aren't free: each one slows down INSERT/UPDATE/DELETE. Write-heavy tables should have fewer; read-heavy tables (reports) can have many.









資料庫選型


六、資料庫選型決策樹




🌳 資料庫選型決策樹




Q1:
需要強 ACID 交易與固定 schema（金融、訂單）？→ 是 → RDBMS（PostgreSQL、MySQL）。


Q2:
只需快取、session、計數器（µs 級延遲）？→ 是 → Redis（KV）。


Q3:
資料結構彈性大、文件巢狀深（CMS、產品目錄）？→ 是 → MongoDB（Document）。


Q4:
關係查詢深（朋友的朋友的推薦）？→ 是 → Neo4j（Graph）。


Q5:
要做 RAG／語義搜尋（embedding 近鄰）？→ 是 → Pinecone / Milvus / pgvector（Vector）。


Q6:
每秒寫入 100 萬以上、可接受最終一致？→ 是 → Cassandra / DynamoDB（Wide-column）。






Q1:
Need strict ACID + fixed schema (finance, orders)? → Yes → RDBMS (PostgreSQL, MySQL).


Q2:
Cache, session, counters (µs latency)? → Yes → Redis (KV).


Q3:
Flexible nested documents (CMS, catalogs)? → Yes → MongoDB (Document).


Q4:
Deep relational queries (friend-of-friend recs)? → Yes → Neo4j (Graph).


Q5:
RAG / semantic search (embedding ANN)? → Yes → Pinecone / Milvus / pgvector (Vector).


Q6:
>1M writes/sec, eventual consistency OK? → Yes → Cassandra / DynamoDB (Wide-column).






💡


2026 趨勢：向量資料庫成為 LLM/RAG 的標配。PostgreSQL + pgvector 擴充模組讓你不用換資料庫就能做語義搜尋。


2026 trend: Vector DBs have become standard infrastructure for LLM/RAG. PostgreSQL + the pgvector extension lets you do semantic search without leaving your existing DB.

# 低階：標準函式庫 sqlite3 / Low-level: stdlib sqlite3
import sqlite3
con = sqlite3.connect("school.db")
cur = con.cursor()
cur.execute("""CREATE TABLE IF NOT EXISTS students
                 (id INTEGER PRIMARY KEY, name TEXT, score REAL)""")
cur.execute("INSERT INTO students(name,score) VALUES (?,?)", ("Ada",95))
con.commit()                       # 結束交易

# JOIN 查詢 / JOIN query
cur.execute("""SELECT s.name, e.course FROM students s
                 INNER JOIN enrollments e ON e.student_id = s.id
                 WHERE s.score > ?""", (80,))
for row in cur.fetchall():
    print(row)

# 高階 ORM：SQLAlchemy 2.x / Modern ORM
from sqlalchemy import create_engine, Column, Integer, String
from sqlalchemy.orm import declarative_base, Session
Base = declarative_base()
class Student(Base):
    __tablename__ = "students"
    id = Column(Integer, primary_key=True)
    name = Column(String); score = Column(Integer)

engine = create_engine("sqlite:///school.db")
with Session(engine) as s:
    s.add(Student(name="Bob", score=88))
    s.commit()


// JOIN 的概念演算法（巢狀迴圈版）/ Conceptual JOIN (nested-loop)
function InnerJoin(left, right, on_left, on_right):
    let result = []
    for l in left:
        for r in right:
            if l[on_left] == r[on_right]:
                result.push(merge(l, r))
    return result
