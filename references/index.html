以下整理計算機概論常見誤解、概念混淆與時下被忽略的細節；部分屬於勘誤，多數屬於補充說明。每則皆附權威來源便於進一步查閱。

Common misconceptions, blurred distinctions, and frequently overlooked details across the Computer Science Intro tutorial; some are errata, most are supplementary notes with authoritative sources for further reading.

補充說明 · Notes

Big-O 是「上界」不是「執行時間」：worst-case vs amortized vs Θ/Ω

教科書常把 Big-O 等同於「時間複雜度」，但嚴格定義 O(f(n)) 只是「漸近上界」（asymptotic upper bound），Θ(f(n)) 才是緊界、Ω(f(n)) 是下界。說「快排是 O(n²)」雖技術上正確卻誤導 — 應說 worst-case Θ(n²)、平均 Θ(n log n)。另外 dynamic array 的 push_back 是 worst-case O(n)（觸發 resize）但 amortized O(1)（Tarjan 1985 accounting method），兩者不可混為「平均」。實務上請明確標註是 worst / average / amortized。

Textbooks often equate Big-O with "running time", but strictly O(f(n)) is only an asymptotic upper bound; Θ(f(n)) is a tight bound and Ω(f(n)) is a lower bound. Saying "quicksort is O(n²)" is technically correct but misleading — say worst-case Θ(n²), average Θ(n log n). Likewise, dynamic-array push_back is worst-case O(n) (on resize) but amortized O(1) (Tarjan's 1985 accounting method); these are not the same as "average". Always state explicitly whether a bound is worst, average, or amortized.

來源：Tarjan 1985 (SIAM J Algebraic Discrete Methods, amortized analysis) · CLRS 4th ed. (2022) ch. 3 & 16

Source: Tarjan 1985 (SIAM J Algebraic Discrete Methods, amortized analysis) · CLRS 4th ed. (2022) ch. 3 & 16

補充說明 · Notes

Stack 與 Heap 不是語言規定的：escape analysis 與「在哪配置」的真相

「primitive 放 stack、object 放 heap」是常見過簡說法。JVM HotSpot 自 Java 6u14（2009）起即透過 escape analysis 與 scalar replacement 將不逃逸的物件配置於 stack 或拆解為暫存器；Go compiler 也用 escape analysis 決定變數實際位置（go build -gcflags="-m" 可觀察）。C++ struct 也可在 heap 上（new）。正確說法：stack/heap 是 runtime 配置策略，不是語言型別的固有屬性；別在面試誤答。

"Primitives live on the stack, objects on the heap" is an oversimplification. JVM HotSpot has used escape analysis with scalar replacement since Java 6u14 (2009) to allocate non-escaping objects on the stack or break them into registers; Go's compiler likewise uses escape analysis to decide actual placement (observable via go build -gcflags="-m"). A C++ struct can also live on the heap (via new). Correct framing: stack vs heap is a runtime allocation strategy, not an inherent property of language types — don't get this wrong in interviews.

Source: OpenJDK HotSpot · Escape Analysis · Go FAQ — stack or heap?

補充說明 · Notes

TCP/IP 4 層 vs OSI 7 層：實務用 4 層，OSI 是教學模型

教科書同時介紹 OSI 7 層與 TCP/IP 4 層，但實際運作的網際網路只實作 TCP/IP 模型（RFC 1122：Link、Internet、Transport、Application）。OSI 模型的 Session（L5）與 Presentation（L6）在實務上幾乎不對應任何具體協定 — HTTPS 的 TLS 同時跨 L5/L6/L7，DNS 也橫跨多層。把交換器叫「L2 設備」、路由器叫「L3 設備」是業界口語，不要把它套回 OSI 七層做精確對位。OSI 1984 標準在 1990 年代基本上輸給 TCP/IP。

Textbooks present both OSI's 7 layers and TCP/IP's 4 layers, but the operational Internet implements only the TCP/IP model (RFC 1122: Link, Internet, Transport, Application). OSI's Session (L5) and Presentation (L6) layers have almost no concrete protocol counterparts in practice — HTTPS's TLS spans L5/L6/L7, and DNS straddles multiple layers. Calling a switch an "L2 device" or a router an "L3 device" is industry shorthand, not a precise OSI mapping. The 1984 OSI standard effectively lost to TCP/IP by the 1990s.

補充說明 · Notes

ACID 與 BASE 不對立；CAP 不是萬能，PACELC 才完整

「SQL = ACID、NoSQL = BASE」屬於誤解。現代分散式 SQL（CockroachDB、Spanner）同樣 ACID 並可水平擴展；MongoDB 自 4.0（2018）起亦支援多文件 ACID 交易。CAP 定理（Brewer 2000；Gilbert & Lynch 2002 正式證明）的「2 選 1」常被過度簡化：實際上 P（分割）不是選項而是常態，真正權衡是 C vs A。Abadi 2012 PACELC 更完整：分割發生時選 P vs A，否則選 L（latency）vs C — 這才解釋為何 DynamoDB「最終一致」是設計選擇而非技術限制。

The slogan "SQL = ACID, NoSQL = BASE" is misleading. Modern distributed SQL (CockroachDB, Spanner) is ACID and horizontally scalable, and MongoDB has supported multi-document ACID transactions since 4.0 (2018). The "pick two" framing of CAP (Brewer 2000; Gilbert & Lynch 2002 proof) is oversimplified — partition tolerance (P) is a fact of life, not a choice; the real trade-off is C vs A. Abadi's 2012 PACELC is more complete: during a partition, choose P vs A; otherwise choose L (latency) vs C — which explains why DynamoDB's eventual consistency is a design choice, not a limitation.

來源：Gilbert & Lynch 2002 (CAP proof, SIGACT News) · Abadi 2012 (PACELC, IEEE Computer)

勘誤注意 · Erratum

量子電腦不是「同時嘗試所有答案」 — 量子優勢來自干涉

最常見的科普誤導是「N qubit 可同時計算 2^N 個答案」。實際上量子演算法的加速來自精心安排的干涉（interference），讓正確答案的振幅相加、錯誤答案彼此相消；最後測量仍只取得一個 classical bit string。Shor 演算法的指數加速是 quantum Fourier transform 的結構，Grover 只給 √N 加速、非指數。Aaronson 多次強調此點：「Quantum is not parallel classical.」NISQ 時代（2026）Google Willow（105 qubit, 2024 Dec）展示糾錯里程碑但仍未達 cryptographically-relevant scale。

The most common pop-science mistake: "N qubits compute 2^N answers in parallel." In reality, quantum speedups arise from carefully engineered interference — amplitudes of correct answers add constructively while wrong ones cancel — and measurement still yields just one classical bit string. Shor's exponential speedup comes from the structure of the quantum Fourier transform; Grover gives only a √N speedup, not exponential. Aaronson stresses repeatedly: "Quantum is not parallel classical." In the NISQ era (2026), Google's Willow chip (105 qubits, Dec 2024) demonstrated an error-correction milestone but still far from cryptographically relevant scale.

補充說明 · Notes

雲端定價的三大「隱形成本」：egress、API 呼叫、vendor lock-in

教科書常以 EC2 / S3 每小時或每 GB 單價估算雲端費用，但實際帳單最痛的三項常被忽略：(1) Egress（離開該雲的傳輸流量）— AWS / GCP / Azure 跨區與外網下載每 GB 約 0.08–0.12 USD，遠高於儲存本身；(2) API 呼叫費（S3 GET / PUT、Lambda invocations）對大量小檔工作流可達數百美元；(3) Vendor lock-in：自管 Kubernetes 數據往 managed 服務（DynamoDB、BigQuery）寫死後遷移成本極高。EU Data Act 2024 已生效規範 egress 並推動可攜性。Cloudflare R2 / Backblaze B2 等 zero-egress 競品近年成長即因此而起。

Textbooks estimate cloud cost from per-hour EC2 or per-GB S3 unit price, but the three line items that bite hardest are routinely missed: (1) Egress — outbound transfer from AWS / GCP / Azure across regions or to the internet runs roughly USD 0.08–0.12 per GB, often dwarfing storage itself; (2) API call fees (S3 GET/PUT, Lambda invocations) can reach hundreds of dollars for many-small-files workflows; (3) Vendor lock-in — once data is wired into managed services (DynamoDB, BigQuery), migration cost is enormous. The EU Data Act 2024 now regulates egress and mandates portability. The recent rise of zero-egress competitors like Cloudflare R2 and Backblaze B2 is a direct response.

補充說明 · Notes

Cache 不只是「比 RAM 快的記憶體」：SRAM/DRAM/cache line/MESI

教科書常把 L1/L2/L3 cache 簡化為「比 RAM 快」，但有幾個關鍵點：(1) Cache 是 SRAM（6T 一 cell，無需 refresh）、主記憶體是 DRAM（1T1C 需 refresh）— SRAM 每位元面積與成本高 6–10 倍，所以 cache 小；(2) Cache 以 cache line（典型 64 B）為單位讀寫，故 struct 排列不當會造成 false sharing — 多核同時寫同一條 line 上的不同變數會觸發 MESI（Modified-Exclusive-Shared-Invalid）反覆同步、效能骨折 10–100 倍；(3) NUMA 架構下跨 socket 訪問遠端 cache 比本地慢 2–3 倍。Drepper《What Every Programmer Should Know About Memory》是這題目的經典。

Textbooks often reduce L1/L2/L3 to "faster than RAM," but several details matter: (1) Cache is SRAM (6 transistors per cell, no refresh); main memory is DRAM (1T1C, requires refresh) — SRAM per-bit area and cost are 6–10× higher, which is why cache is small; (2) Caches read and write in cache-line units (typically 64 B), so poor struct layout causes false sharing — two cores writing distinct variables on the same line trigger repeated MESI (Modified-Exclusive-Shared-Invalid) syncs and 10–100× slowdowns; (3) Under NUMA, cross-socket access to remote cache is 2–3× slower than local. Drepper's "What Every Programmer Should Know About Memory" remains the canonical reference.
