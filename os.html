CHAPTER 6 / 16

作業系統

作業系統是硬體與應用程式之間的「翻譯層」——管理 CPU、記憶體、檔案、I/O，並提供行程、執行緒、虛擬化等抽象。本章從 Unix 的誕生，講到你 sbatch 提交 BWA 任務時 SLURM 為你做的一切。

An OS is the translation layer between hardware and applications — managing CPU, memory, files, I/O — and exposing abstractions like processes, threads, and virtualization. From the birth of Unix to what SLURM does when you sbatch a BWA job.

Unix 的誕生

1969 年貝爾實驗室的兩個年輕人

1969 年夏天，貝爾實驗室剛剛退出一個失敗的多用戶作業系統計畫（Multics）。29 歲的 Ken Thompson 和 27 歲的 Dennis Ritchie 沒事做，找到一台幾乎沒人用的 PDP-7（只有 8 KB RAM）。Thompson 想玩自己寫的「太空旅行 (Space Travel)」遊戲——但是太慢了。為了讓遊戲跑得動，他乾脆寫了一個全新的、超精簡的作業系統。Ritchie 接著為了讓 OS 可以「跨機器移植」，發明了一個全新的程式語言——C。

這個 OS 後來叫 Unix。它最革命性的設計：「一切都是檔案」（硬碟、終端機、印表機、網路連線都可用 open/read/write/close 操作）、「小工具 + pipe」（每個命令做一件事，組合起來解大問題）。

2026 年的今天：全球 96% 的伺服器跑 Linux（Unix 的開源後裔）；75% 的智慧型手機跑 Android（基於 Linux）；macOS 與 iOS 基於 Darwin（BSD Unix）；你的雲端 K8s 集群、HPC 叢集、Snakemake pipeline 都跑在 Unix-like 系統上。兩個程式員的副業 60 年後改變了世界——這就是好抽象的力量。

Summer 1969 — Bell Labs had just pulled out of a failed multi-user OS project (Multics). With nothing to do, 29-year-old Ken Thompson and 27-year-old Dennis Ritchie found a barely-used PDP-7 (just 8 KB RAM). Thompson wanted to play his own game "Space Travel" — but it was too slow. So he wrote a tiny new OS from scratch to make it runnable. Ritchie, wanting the OS to be portable across machines, then invented a new programming language: C.

That OS became Unix. Its most revolutionary ideas: "everything is a file" (disks, terminals, printers, network connections — all manipulable via open/read/write/close) and "small tools + pipes" (each tool does one thing; compose to solve big problems).

Today, 2026: 96% of servers run Linux (Unix's open-source heir); 75% of smartphones run Android (Linux-based); macOS and iOS are built on Darwin (BSD Unix); your K8s clusters, HPC nodes, Snakemake pipelines all run on Unix-likes. A two-person side project changed the world 60 years later — the power of good abstractions.

💡
核心觀念：OS 的兩大角色是「資源管理者」（公平分配 CPU/RAM/I/O）與「抽象層」（提供檔案、行程、socket 等概念，隱藏硬體細節）。 Core idea: An OS plays two roles — resource manager (fairly allocate CPU/RAM/I/O) and abstraction layer (expose files, processes, sockets — hiding hardware details).
四大職責

一、核心概念

⚙️

① CPU 排程

決定哪個行程下一個跑、跑多久。算法：FCFS、SJF、Round Robin、Priority、MLFQ、Linux CFS。目標：平均等待時間最短 vs 公平 vs 即時反應。

Decides which process runs next and for how long. Algorithms: FCFS, SJF, RR, Priority, MLFQ, Linux CFS. Goals: min avg wait vs fairness vs responsiveness.

🧠

② 記憶體管理

虛擬位址 ↔ 實體位址、分頁 (paging)、保護 (protection)、swap、Page Fault 處理。讓每個程式以為自己擁有整個記憶體。

Virtual ↔ physical addresses, paging, protection, swap, page-fault handling. Each program believes it owns all of memory.

📁

③ 檔案系統

提供目錄、檔名、權限 (rwx)、持久儲存、inode、journaling。讓「位元」變成「檔案」這個高階抽象。

Provides directories, filenames, permissions (rwx), persistence, inodes, journaling. Turns "bits" into the high-level abstraction of "files."

🔌

④ I/O 與驅動

統一鍵盤、滑鼠、網卡、GPU 介面。中斷 (interrupt)、DMA、device driver。讓應用程式無需理會具體硬體型號。

Unifies keyboard, mouse, NIC, GPU interfaces. Interrupts, DMA, drivers. Apps don't need to know hardware models.

Kernel 模式 vs User 模式

現代 CPU 至少有兩種權限環 (privilege ring)：

  • Kernel mode (Ring 0)：可執行所有指令、存取所有記憶體、操作硬體。OS kernel 本身在這跑。
  • User mode (Ring 3)：禁止存取 I/O、不能改 page table、不能執行特權指令。你的所有應用程式（Chrome、Python、BWA）都在這跑。

App 要做 I/O（讀檔、開 socket、配置記憶體）必須透過 system call (syscall) 切換到 kernel mode——這個切換有成本（~100 ns），是為何效能瓶頸常常是「syscall 太頻繁」（用 strace 看）。

Modern CPUs have at least two privilege rings:

  • Kernel mode (Ring 0): can run any instruction, access any memory, drive hardware. The OS kernel lives here.
  • User mode (Ring 3): no direct I/O, no page-table edits, no privileged ops. All your apps (Chrome, Python, BWA) run here.

To do I/O (read a file, open a socket, allocate memory) an app must syscall into kernel mode — costing ~100 ns. Performance often bottlenecks on "too many syscalls" (use strace to debug).

Process vs Thread / 同步 / 死結

三、深入剖析

3.1 Process vs Thread

行程 (Process) 是「正在執行中的程式」——擁有獨立的位址空間、檔案描述符、PID。執行緒 (Thread) 是行程內的執行單位，共享同一份記憶體與檔案，但有自己的暫存器與堆疊。

fork() 複製整個父行程（含記憶體 copy-on-write）；exec() 載入新程式覆蓋目前位址空間。Linux 用 PCB (Process Control Block)，內容包括 PID、暫存器快照、open files、page table 指標、訊號掩碼等。切換行程必須儲存/還原所有暫存器，這就是 context switch，成本約 1–10 μs（執行緒切換約 1 μs，行程切換更貴因為要刷新 TLB）。

A process is a "program in execution" with its own address space, file descriptors, and PID. A thread is an execution unit inside a process — sharing memory and files but with its own registers and stack.

fork() duplicates the parent process (memory copy-on-write); exec() loads a new program over the current address space. Linux uses a PCB (Process Control Block) with PID, register snapshot, open files, page-table pointer, signal mask, etc. Switching processes requires saving/restoring all registers — the context switch, costing 1–10 μs (threads ~1 μs; processes more because the TLB is flushed).

3.2 同步機制

多執行緒共享記憶體時，若兩個執行緒同時讀寫同一變數，會出現 競態 (race condition)。OS 提供兩大同步原語：

  • Mutex（互斥鎖）：同一時間只有 1 個執行緒能持有，常用於保護臨界區 (critical section)。
  • Semaphore（號誌）：計數器，允許 N 個執行緒同時通過——可實作生產者-消費者問題。
  • Condition Variable：讓執行緒「等到某條件成立」才繼續。
  • RWLock：讀者多寫者少的場景，允許多個讀者並行、寫者獨佔。

When threads share memory, simultaneous reads/writes cause race conditions. OSes provide synchronization primitives:

  • Mutex: held by exactly one thread at a time — protects critical sections.
  • Semaphore: counter allowing N concurrent threads — used in producer-consumer.
  • Condition variable: wait until a predicate becomes true.
  • RWLock: many readers + one writer — read-heavy workloads.

3.3 死結四條件

🌳 Deadlock 四條件

①
互斥 (Mutual exclusion) → 資源同時只能被一個行程持有。
②
持有並等待 (Hold and wait) → 行程持有資源時還能等待新資源。
③
不可搶佔 (No preemption) → 資源不能被強制收回。
④
循環等待 (Circular wait) → 形成「行程 A 等 B 等 C 等 A」的環。
①
Mutual exclusion → resources held exclusively.
②
Hold and wait → processes hold while waiting for more.
③
No preemption → resources cannot be forcibly taken back.
④
Circular wait → A waits B waits C waits A — a cycle.
⚠️
破壞任一條件即可避免死結。實務常用「資源排序」（永遠按固定順序取鎖）來破壞 ④ 循環等待。
Break any one condition to avoid deadlock. Common practice: resource ordering (always lock in a fixed global order) — breaks #4 circular wait.
五個經典時刻

四、五個經典故事

1991：21 歲的 Linus

1991 年 8 月 25 日，芬蘭赫爾辛基大學 21 歲學生 Linus Torvalds 在 Usenet 新聞群組 comp.os.minix 貼文：「我在做一個（免費的）作業系統（只是嗜好，不會像 GNU 那樣大而專業）……」。他當時只是想做出一個能在自己 386 PC 上跑的 Minix 替代品。35 年後，Linux 跑在從智慧手機到超級電腦的所有東西上，包括火星探測車和 SpaceX 火箭。Linux Foundation 估計 Linux 內核的開發成本若由單一公司承擔，相當於 數百億美元。

August 25, 1991 — 21-year-old Helsinki university student Linus Torvalds posted to Usenet's comp.os.minix: "I'm doing a (free) operating system (just a hobby, won't be big and professional like gnu)..." He just wanted a Minix replacement for his 386 PC. 35 years later, Linux runs everything from smartphones to supercomputers, including Mars rovers and SpaceX rockets. The Linux Foundation estimates the kernel's development cost (if borne by one company) would be tens of billions of dollars.

1985–87：Therac-25 醫療悲劇

加拿大原子能公司製造的 Therac-25 放射治療機 1985–87 年間在美加致少 6 名患者死於放射過量。根本原因：OS 同步程式碼裡的 race condition。當操作員快速修改設定時，輸入處理執行緒與磁鐵控制執行緒之間有時序錯誤，導致機器照射 100 倍正常劑量的高能電子束。Nancy Leveson 的事後分析（1993）成為軟體工程倫理教科書必讀——「沒有硬體互鎖、只靠軟體確保安全」是致命的。

Canada's Atomic Energy-built Therac-25 radiation therapy machine killed at least 6 patients in the US and Canada from 1985–87 via radiation overdose. Root cause: a race condition in the OS sync code. When operators changed settings quickly, the input thread and magnet-control thread had a timing bug, blasting patients with 100× the intended electron beam. Nancy Leveson's 1993 analysis became a required reading in SE ethics — "no hardware interlock, software-only safety" is fatal.

2010：Stuxnet 蠕蟲

2010 年發現的 Stuxnet 蠕蟲被廣泛認為是美國/以色列聯合開發的網路武器，目標是伊朗納坦茲鈾濃縮廠的離心機。它利用 Windows 四個 0-day 漏洞（前所未見的奢侈）穿透氣隙網路 (air-gapped network)，找到特定型號的 Siemens PLC，並讓離心機在維持顯示「正常」的同時加速到爆炸。估計毀掉 1000+ 台離心機。Stuxnet 證明了 OS 漏洞可以是國家級武器，從此 0-day 黑市價飆漲。

Stuxnet (discovered 2010), widely attributed to a US/Israel cyberweapon, targeted centrifuges at Iran's Natanz uranium enrichment plant. It used four Windows 0-day vulnerabilities (unheard-of luxury) to cross the air-gapped network, located specific Siemens PLCs, and spun centrifuges to destruction while showing "normal" on dashboards. Estimated to have destroyed 1000+ centrifuges. Stuxnet proved OS vulnerabilities are nation-state weapons — 0-day black-market prices skyrocketed afterward.

2001：Darwin 與 macOS

Steve Jobs 重返 Apple 時，把 NeXTSTEP 改造為新的 Mac OS X (2001)。底層是 Darwin——免費開源、結合 FreeBSD 的網路與檔案系統 + Mach 3.0 微核（Pittsburgh CMU 的研究專案）。「微核」設計把驅動程式與檔案系統推到 user mode，理論上更穩定（一個驅動崩潰不會拖垮整個系統），但 IPC 開銷大。Linux 走相反路線（monolithic kernel）。25 年後兩種設計各有勝場，這就是「沒有銀彈」的活教材。

When Steve Jobs returned to Apple, he turned NeXTSTEP into Mac OS X (2001). Its foundation is Darwin — free and open-source, combining FreeBSD's networking and FS with the Mach 3.0 microkernel (a CMU research project). "Microkernel" design pushes drivers and FS into user mode — theoretically more stable (a driver crash won't sink the system), but IPC is expensive. Linux took the opposite path (monolithic). 25 years on, both designs thrive — a living "no silver bullet" lesson.

2008：Android 的雙層架構

Google 收購 Android (2005) 後，選擇 Linux kernel 作為基底（穩定、免費、有龐大驅動生態）+ 自家 Dalvik VM（後改為 ART）跑 Java 應用。為何不用直接的 Linux app？因為 ARM 手機規格差異大、要省電省記憶體——VM 提供統一的 JIT/AOT 與電源管理。今天 Android 佔全球手機 OS 市場 70%+，是 Linux 跑得最廣的形式（雖然大多數使用者不知道）。

After acquiring Android (2005), Google chose the Linux kernel as the base (stable, free, huge driver ecosystem) + its own Dalvik VM (later ART) to run Java apps. Why not native Linux apps? Because ARM phone specs vary wildly and battery/RAM are tight — the VM provides unified JIT/AOT and power management. Today Android owns 70%+ of global mobile OS share — the most widely deployed Linux form (most users don't know it).

生資連結（續）

六、🧬 給生物資訊學家

🧬
① SLURM 就是 HPC 上的 OS

當你 sbatch align.sh 把一個 BWA 任務送上學術 HPC，SLURM 做的事和 Linux CFS 排程器幾乎一樣，只是把單位從「執行緒」放大到「整個運算節點」。FCFS + backfill + fairshare：先到先服務、但允許短工作插隊填補空檔。你的 --time=2:00:00 --mem=64G --cpus-per-task=16 就是給 scheduler 的「burst time」與資源需求宣告。寫對了 BWA 1 小時跑完；寫錯（mem 估太低）可能在隊伍裡卡 3 天。

When you sbatch align.sh a BWA job on academic HPC, SLURM does what Linux's CFS scheduler does — scaled from "thread" to "whole node." FCFS + backfill + fairshare: first-come-first-served, short jobs sneak into idle gaps. Your --time=2:00:00 --mem=64G --cpus-per-task=16 is your burst-time + resource declaration. Right → BWA in 1h; wrong (too little mem) → 3-day queue wait.

🧬
② Conda / Mamba：輕量虛擬化

不同 bioinformatics 工具要求不同 Python、R、系統函式庫。Conda（與更快的 Mamba、2024+ 的 Pixi）做的事跟 OS 行程隔離原理相同——每個 env 是獨立的 $PATH + 函式庫樹。優點：秒級啟用、無 Docker 開銷、跨 Linux/macOS。HPC 上 90% 工作流仍用 Conda，因為通常沒 root。

Tools need different Python, R, system libs. Conda (with faster Mamba and 2024+ Pixi) is like OS process isolation — each env is a separate $PATH + library tree. Pros: sub-second activation, no Docker overhead, cross-platform. 90% of HPC workflows still use Conda because root is rare.

🧬
③ 容器化與 nf-core

nf-core 80+ 個 peer-reviewed Nextflow pipeline 的每個 step 都對應一個 BioContainers Docker image——要在 100 位研究者的 100 台機器上得到一致結果，OS-level 容器化是唯一解。Singularity / Apptainer 是 HPC 友善的替代品——無 root daemon、image 是單檔 .sif。docker pull 在 HPC 通常被擋。

nf-core's 80+ peer-reviewed Nextflow pipelines bind each step to a BioContainers Docker image — for identical results across 100 machines, OS-level containerization is the only answer. Singularity / Apptainer are HPC-friendly — no root daemon, single .sif image. docker pull is usually blocked on HPC.

🧬
④ 檔案系統怎麼選

HPC 跑 BWA/STAR，FASTQ 50–200 GB、SAM 中間檔 100 GB+，檔案系統選對與否決定 pipeline 跑 6 小時還是 6 天。
• ext4 / XFS：單機本地，最快（NVMe 7 GB/s）。
• NFS：經典網路 FS，單伺服器是瓶頸；大量小檔很慢。
• Lustre / BeeGFS：平行 FS、HPC 標準，可達 100+ GB/s。
• S3：雲端標準、HTTPS API、無 POSIX。

HPC BWA/STAR with 50–200 GB FASTQ + 100 GB+ SAM — filesystem choice decides 6-hour vs 6-day.
• ext4 / XFS: local, fastest (NVMe 7 GB/s).
• NFS: classic shared FS, single-server bottleneck; awful with small files.
• Lustre / BeeGFS: parallel, HPC standard, 100+ GB/s.
• S3: cloud, HTTPS API, no POSIX.

🧬
⑤ Snakemake 並行的本質

Snakemake 的「每個 rule 是一個 process」本質就是 fork+exec。100 個樣本的 align = 100 個獨立 OS process，由 Linux scheduler 或 SLURM 分配。比執行緒池更穩健（一個樣本崩潰不影響其他），可跨節點分布。代價：每個 process 要 re-load index（BWA 索引重複載入 100 次浪費 cache）。

Snakemake's "each rule is a process" is essentially fork+exec. Aligning 100 samples = 100 separate OS processes via Linux/SLURM scheduler. More robust than thread pools (one crash doesn't sink all), distributable. Trade-off: each re-loads indices (BWA index loaded 100×, wasting cache).

import threading, multiprocessing

def cpu_work(n):
    s = 0
    for i in range(n): s += i*i
    return s

常見陷阱

九、常見誤解

❌ Linux 沒有病毒

真相：Linux 桌面市佔低所以「桌面惡意軟體」少；但 Linux 伺服器是最被攻擊的平台。Mirai、Log4Shell 每天都發生。HPC 帳號被入侵挖礦的案例屢見不鮮。請務必 SSH 用 key、fail2ban、unattended-upgrades。

Truth: Low desktop share means few desktop attacks; but Linux servers are the most-attacked platform. Mirai, Log4Shell daily. HPC accounts hijacked for crypto mining. SSH keys, fail2ban, unattended-upgrades — always.

❌ 多執行緒一定更快

真相：Python GIL 讓同時刻只 1 個執行緒能跑 bytecode。CPU-bound 用 threading 不會加速。要 multiprocessing。Python 3.13 才有實驗 no-GIL。

Truth: Python's GIL means only one thread runs bytecode at a time. CPU-bound threading rarely helps. Use multiprocessing. Python 3.13 has experimental no-GIL.

❌ 容器 = 輕量 VM

真相：VM 虛擬化整台機器（含 guest kernel）；容器只是 Linux namespace + cgroup。所有容器共享 host kernel——Linux 容器不能跑 Windows kernel；macOS Docker Desktop 底下其實是 Linux VM。

Truth: A VM virtualizes the whole machine (with guest kernel); a container is just Linux namespaces + cgroups, sharing host kernel. Linux containers can't run Windows kernel; macOS Docker Desktop hides a Linux VM.

❌ fork 沒有副作用

真相：Python multiprocessing 預設 fork——若已啟動執行緒（BLAS、PyTorch DataLoader），fork 後鎖狀態是「未定義行為」，可能 deadlock。macOS Python 3.8+ 預設 spawn。set_start_method('spawn') 是更安全的選擇。

Truth: Python multiprocessing defaults to fork — but if threads have started (BLAS, PyTorch DataLoader), child lock state is undefined; possible deadlocks. macOS Python 3.8+ defaults to spawn. set_start_method('spawn') is safer.

十、延伸思考

  1. WSL 模糊 OS 界線？
    WSL 2 在 Windows 內跑真實 Linux kernel；macOS Docker Desktop 也是 Linux VM。對 bioinformatician：Conda、Snakemake、Python 全跨平台——你還需要在意 Linux vs Windows vs macOS 嗎？ WSL 2 runs a real Linux kernel inside Windows; macOS Docker Desktop is a hidden Linux VM. For bioinformaticians, Conda/Snakemake/Python are cross-platform — does Linux vs Windows vs macOS still matter?
  2. Rust 寫的 OS 會取代 Linux 嗎？
    Linux 70% 安全漏洞來自 C 記憶體錯誤。Rust 編譯期消除這類錯誤。Redox OS 全用 Rust。但生態系挑戰巨大——30 年累積的驅動。歷史上「技術更優」的 OS（Plan 9、BeOS、Haiku）都失敗。 70% of Linux CVEs are C memory bugs. Rust's ownership eliminates these at compile time. Redox OS is full-Rust. But ecosystem-wise impossible — 30 years of drivers. Plan 9, BeOS, Haiku all failed despite being "technically better."
