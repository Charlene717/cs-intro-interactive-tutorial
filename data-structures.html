資料結構

一張 1 GB 的人類基因組 FASTA，用錯資料結構查 BRCA1 位置可能要 10 分鐘；用對結構只要 0.01 秒——快 60,000×。資料結構是程式設計的「骨架」。

A 1 GB human-genome FASTA: looking up BRCA1 with the wrong data structure may take 10 minutes; with the right one, 0.01 seconds — 60,000× faster. Data structures are the skeleton of programming.

60,000× 的差距

同一個檔案，60,000 倍的差距

假設你有一個 1 GB 的 hg38.fa 人類參考基因組。你想知道 BRCA1 基因從第幾個 byte 開始。怎麼找？

  • 方法 A：用 Python 開檔，for line in f: if "BRCA1" in line: ...——掃整個 1 GB 檔案。耗時 10 分鐘。
  • 方法 B：先用 samtools faidx hg38.fa 建立 .fai 索引（一個小檔，內含每條染色體在 FASTA 的位元組偏移）；再用 samtools faidx hg38.fa chr17:43044295-43170245。耗時 0.01 秒。

差距 60,000 倍。差別在哪？方法 A 用的是 list/sequential scan；方法 B 用的是 hash table + B-tree-style index。選對資料結構，速度勝過任何硬體升級。

這一章不只教你「array vs list」，它要回答：為什麼 BAM 一定要有 .bai？為什麼 SPAdes 用 de Bruijn graph 做組裝？為什麼 BLAST 用 hash table 找 k-mer？

Suppose you have a 1 GB hg38.fa human reference genome. You want to know at which byte offset BRCA1 starts. How?

  • Method A: open in Python, for line in f: if "BRCA1" in line: ... — scans the entire 1 GB. Takes 10 minutes.
  • Method B: run samtools faidx hg38.fa once to build a .fai index (a small file mapping each chromosome to its byte offset); then samtools faidx hg38.fa chr17:43044295-43170245. Takes 0.01 seconds.

That's 60,000×. The difference: Method A uses a list/sequential scan; Method B uses a hash table + B-tree-style index. Picking the right data structure beats any hardware upgrade.

This chapter isn't just "array vs list." It answers: why does BAM always need a .bai? Why does SPAdes use de Bruijn graphs for assembly? Why does BLAST hash k-mers?

💡
核心觀念：資料結構 = 資料的「組織方式」+ 一組可用的「操作」。同一份資料以不同結構儲存，搜尋、插入、刪除、範圍查詢的複雜度天差地別。沒有最好的結構，只有最配合「工作負載 (workload)」的結構。 Core idea: A data structure = data's organization + a set of operations. The same data, stored differently, has wildly different complexities for search / insert / delete / range queries. There is no "best" structure — only the one that fits your workload.
核心：八大結構

一、八大資料結構速覽

📚

Array / List 線性

連續記憶體格子，索引存取 O(1)、中間插入 O(n)。Python list、NumPy array、C array、Rust Vec 全是這類。cache friendly，是最常用的結構。

Contiguous memory cells. Index access O(1), middle insert O(n). Python list, NumPy array, C array, Rust Vec — all this family. Cache-friendly, the most common structure.

🔗

Linked List 線性

每個節點存「資料 + 下一節點 pointer」。頭插 O(1)、中間插 O(1)（若已有指標），但 索引存取 O(n)。實務少用（cache 不友善），但 OS kernel 的 task list、Lisp 全靠它。

Each node holds "data + pointer to next." Head insert O(1), middle insert O(1) (if you have a pointer), but index access O(n). Less used in practice (cache-unfriendly), but OS kernel task lists and Lisp depend on it.

📥

Stack (LIFO) 線性

後進先出。push/pop 都 O(1)。函式呼叫的 call stack、HTML 解析、撤銷 (Ctrl-Z) 全用 Stack。Python list 加 append/pop 就是 stack。

Last in, first out. push/pop both O(1). Function call stacks, HTML parsing, undo (Ctrl-Z) — all stacks. Python list with append/pop is a stack.

📤

Queue / Deque 線性

先進先出 (FIFO)，enqueue/dequeue O(1)。BFS 走訪、列印佇列、任務排程。collections.deque 是雙端 queue。

First in, first out. enqueue/dequeue O(1). BFS traversal, printer queue, task scheduling. collections.deque is double-ended.

🗂️

Hash Table 雜湊

用 hash function 把 key 映射到 array 索引。平均 O(1)，最壞 O(n)（collision）。Python dict、Java HashMap、C++ unordered_map、Redis 全部是 hash table。是最常用的「快速查找」結構。

A hash function maps keys to array indices. Average O(1), worst O(n) (collisions). Python dict, Java HashMap, C++ unordered_map, Redis — all hash tables. The most common "fast lookup" structure.

🌳

Tree (BST/AVL/RB) 樹

每節點有最多兩個子節點，左子小、右子大。平衡樹（AVL、Red-Black）保證搜尋/插入/刪除 O(log n)。C++ std::map、Java TreeMap、Linux 完全公平排程器全用 RB Tree。

Each node has up to two children, left smaller, right larger. Balanced trees (AVL, Red-Black) guarantee O(log n) for search/insert/delete. C++ std::map, Java TreeMap, Linux CFS scheduler — all RB Trees.

⛰️

Heap (Binary Heap) 樹

完全二元樹，min-heap：父節點 ≤ 子節點。取最小 O(1)、插入/刪除 O(log n)。實作 priority queue、Dijkstra、heapsort 的核心。Python heapq。

Complete binary tree. Min-heap: parent ≤ children. Get-min O(1), insert/delete O(log n). Core of priority queues, Dijkstra, heapsort. Python heapq.

🕸️

Graph 圖

節點 (vertex) + 邊 (edge)。可有向/無向、加權/無加權。表示法：① adjacency matrix V² 空間；② adjacency list V+E 空間。社群網路、基因組組裝 (de Bruijn graph)、蛋白質網路都是 graph。

Vertices + edges. Directed/undirected, weighted/unweighted. Representations: (1) adjacency matrix V² space; (2) adjacency list V+E space. Social networks, genome assembly (de Bruijn graphs), protein interaction networks — all graphs.

Hash, Tree, Trie

三、深入剖析：Hash, Tree, Trie

3.1 Hash function 與 collision 處理

Hash function 把任意 key 映射到固定範圍 [0, m) 的整數。理想性質：① 均勻分佈、② 易計算、③ 雪崩效應（input 變一個 bit，output 大幅改變）。

常見 hash：FNV-1a (簡單)、MurmurHash3 (快、非加密)、SipHash (Python 預設，抗 hash flooding 攻擊)、SHA-256 (加密用)。

Collision 處理：① Chaining：每個 bucket 是 linked list（Java HashMap 用此，超過 8 個轉成 RB Tree）；② Open addressing：碰撞時找下一個空格（線性探測 / quadratic / 雙重 hashing）。

Load factor：α = n/m。當 α > 0.75 通常 resize（rehash 全部）。

A hash function maps any key into [0, m). Ideal properties: (1) uniform distribution, (2) cheap to compute, (3) avalanche (1-bit input change → big output change).

Common hashes: FNV-1a (simple), MurmurHash3 (fast, non-crypto), SipHash (Python default, resists hash-flooding attacks), SHA-256 (cryptographic).

Collision handling: (1) Chaining — each bucket is a linked list (Java HashMap, >8 entries becomes RB Tree); (2) Open addressing — probe forward on collision (linear / quadratic / double hashing).

Load factor: α = n/m. Usually resize (rehash all) when α > 0.75.

3.2 為何要「旋轉」？平衡的代價

未平衡的 BST：若按順序插入 1,2,3,4,5，會退化成 linked list (O(n))。AVL Tree：每節點存 balance factor (左高-右高)，超過 ±1 就做 LL/RR/LR/RL 旋轉。Red-Black Tree：放寬條件 (允許 height 差 2 倍)，插入/刪除旋轉次數較少，實務最常用。

Unbalanced BST: insert 1,2,3,4,5 in order → degenerates to a linked list (O(n)). AVL Tree: each node stores a balance factor (left-height − right-height); >±1 triggers LL/RR/LR/RL rotation. Red-Black Tree: looser invariant (height ratio up to 2×), fewer rotations on insert/delete — the practical workhorse.

3.3 Trie：前綴搜尋的王者

Trie (前綴樹) 把字串按字元逐層展開——所有共享前綴的字串走同一條路徑。查找 O(m) (m = 字串長度)，與字串總數無關！自動完成 (autocomplete)、IP 路由表 (longest prefix match)、拼字檢查、生物序列前綴搜尋皆用。

變種：Radix Tree (壓縮 Trie)，把單一子節點的路徑合併，省空間。Linux kernel 用 radix tree 管 page cache。

Trie (prefix tree) spreads strings character-by-character — all strings sharing a prefix follow one path. Search O(m) (m = string length), independent of total strings! Used in autocomplete, IP routing (longest prefix match), spell-check, bio prefix search.

Variants: Radix Tree (compressed Trie) collapses single-child paths to save space. Linux kernel uses radix trees for the page cache.

3.4 圖的兩種表示法

Adjacency matrix：V×V 矩陣，M[i][j]=1 表示有邊。檢查邊存在 O(1)，但空間 O(V²)，不適合稀疏圖。
Adjacency list：每節點存「鄰居 list」。空間 O(V+E)，但檢查邊 O(degree)。基因組組裝的 de Bruijn graph (數百萬節點) 必用 adjacency list。

Adjacency matrix: V×V matrix, M[i][j]=1 if edge exists. Edge check O(1), but space O(V²) — bad for sparse graphs.
Adjacency list: each node stores a neighbor list. Space O(V+E), edge check O(degree). Genome-assembly de Bruijn graphs (millions of nodes) require adjacency lists.

五個傳奇結構

四、五個傳奇結構的故事

① Hash Table (1953) — IBM Hans Peter Luhn

1953 年 IBM 的 Hans Peter Luhn（也是 KWIC 索引發明者）首次在內部備忘錄提出「chaining hash table」。他原本要做的是「IBM 客戶資料庫的快速查詢」。同年他還發明了「Luhn algorithm」——至今所有信用卡號碼最後一位的 check digit。

In 1953, IBM's Hans Peter Luhn (also creator of the KWIC index) first proposed "chaining hash tables" in an internal memo. He was building "fast IBM customer-database lookups." Same year he invented the "Luhn algorithm" — still the check digit on every credit-card number today.

② AVL Tree (1962) — 莫斯科

1962 年蘇聯數學家 Adelson-Velsky & Landis 在莫斯科發表第一個「自平衡 BST」——以兩人姓氏首字母命名 AVL Tree。冷戰時期，西方 4 年後才看到譯本。AVL 保證 O(log n)，但插入旋轉較頻繁；後來 1972 Bayer 發明 B-Tree，1978 Guibas & Sedgewick 發明 Red-Black Tree。

In 1962, Soviet mathematicians Adelson-Velsky & Landis published the first self-balancing BST in Moscow — named AVL Tree after their initials. Cold War: the West only saw the translation 4 years later. AVL guarantees O(log n) but rotates often on insert; later Bayer invented B-Trees (1972) and Guibas & Sedgewick invented Red-Black Trees (1978).

③ B-Tree (1972) — 資料庫的核心

1972 年 Rudolf Bayer & Ed McCreight 在 Boeing 研究室設計 B-Tree——每節點可有多個 key（典型 100+），高度極矮，極適合「磁碟存取」。今天每一個 SQL 資料庫的索引、檔案系統的目錄、BAM 的 .bai 都是 B-Tree 或其變種 (B+Tree)。

In 1972 Rudolf Bayer & Ed McCreight at Boeing designed B-Tree — each node holds many keys (typically 100+), keeping the tree very flat, perfect for disk access. Today every SQL database index, filesystem directory, and BAM .bai is a B-Tree or variant (B+Tree).

④ Trie (1971) — Edward Fredkin 在 IBM

Trie 名稱來自 "retrieval"（讀作 try）。1959 年 René de la Briandais 提出概念，1960 Edward Fredkin 正式命名與分析。MIT AI Lab 創辦人之一，後來研究數位物理 (digital physics)。Trie 在 1970s 用於拼字檢查器，今天用於 Google search autocomplete。

Trie comes from "retrieval" (pronounced "try"). Briandais sketched it in 1959; Fredkin formally named and analyzed it in 1960. Co-founder of the MIT AI Lab, later worked on digital physics. Tries powered spell-checkers in the 1970s; today they back Google's autocomplete.

⑤ Bloom Filter (1970) — Burton Howard Bloom

1970 年 MIT 學生 Burton Bloom 為了「拼字檢查器在 64 KB 記憶體裡塞下整本字典」而發明 Bloom Filter——犧牲精確性換空間：可能誤判「有」，但絕不漏報「無」。今天用於 Google Bigtable 跳過不存在的 row、瀏覽器 檢查惡意網址、生資 k-mer 計數 (Cuttlefish, KMC3) 與 序列檢索 (BIGSI)。

In 1970 MIT student Burton Bloom invented Bloom Filter to fit a whole dictionary into 64 KB for spell-checking — trading accuracy for space: it may say "yes" wrongly, but never "no" wrongly. Today used in Google Bigtable to skip absent rows, browsers for malware-URL checks, and in bio: k-mer counters (Cuttlefish, KMC3) and sequence retrieval (BIGSI).

⑥ Skip List (1989) — William Pugh

1989 年 Maryland 大學 William Pugh 發明 Skip List——一種「機率資料結構」，用 linked list 的多層來模擬 BST。實作比 RB Tree 簡單 50%，效能相當。Redis 的 sorted set (ZSET)、LevelDB、RocksDB 內部都是 Skip List。

In 1989 Maryland's William Pugh invented Skip List — a probabilistic structure stacking linked lists to mimic a BST. 50% less code than RB Tree, comparable performance. Redis sorted sets (ZSET), LevelDB, RocksDB all use Skip Lists internally.

🧬 給生物資訊學家

六、🧬 生資連結：資料結構撐起整個生資生態系

每個 bioinformatics 工具背後，都有一個關鍵資料結構選擇。學會這些，你能瞬間看出新工具的速度從哪裡來。

1. de Bruijn Graph — 短 read 組裝的靈魂

SPAdes (Bankevich 2012)、Velvet (Zerbino 2008)、SOAPdenovo 都用 de Bruijn graph：把每個 k-mer (k=21~127) 當節點，相鄰 k-mer 連邊。組裝 = 在圖中找 Eulerian path。記憶體需求 = k-mer 數量 × 節點大小——這是為什麼大基因組組裝動輒需要 TB 級 RAM。

2. String Graph / OLC — 長 read 組裝

Canu (Koren 2017)、HiCanu、Flye 用 Overlap-Layout-Consensus + string graph：每條 read 是節點，overlap > 1 kb 連邊。長 read (PacBio HiFi, ONT) 比短 read 更適合 string graph，因為 overlap 訊號強。

3. Hash Table — BLAST 與 k-mer 計數

BLAST 把 query 切成 11-mer，用 hash table 索引整個資料庫。KMC3、Jellyfish 都是 k-mer 計數工具，核心是大型 hash table（最佳化版本用 minimizer 降低記憶體）。

4. Suffix Tree / Suffix Array — 序列搜尋的理論最佳

Suffix Tree (McCreight 1976) 可在 O(m) 找出 pattern——但建構需 O(n) 時間 + O(n·20) 空間，對人類基因組需 60+ GB。Suffix Array (Manber & Myers 1990) 空間更省。STAR aligner 用 Suffix Array 索引基因組。

5. B-tree / R-tree — BAM 索引 + BED 區間查詢

BAM 索引 .bai 用「bin scheme + linear index」（類似 B-tree），讓 samtools view chr1:1000-2000 在毫秒內定位。BEDtools、tabix 用 R-tree / interval tree，O(log n + k) 查找區間 overlap（k = 結果數）。GenomicRanges (R/Bioconductor) 也是。

6. Bloom Filter — k-mer 是否存在 / sequence retrieval

Cuttlefish 2 用 Bloom filter 減少 k-mer 計數記憶體。BIGSI (Bradley 2019) 與 COBS 用 Bloom filter 在 PB 級序列資料庫中快速判斷「query 是否可能存在」——空間極省，誤判率可控。

7. Priority Queue / Heap — Genome Browser 渲染與 Dijkstra

IGV / JBrowse 顯示多軌時用 priority queue 排序事件。HISAT2 的 graph traversal、Bandage 的圖視覺化都靠 priority queue。Dijkstra 找最短路徑 (e.g., haplotype graph) 必用 min-heap。

8. Trie / Aho-Corasick — 短序列匹配與 motif 搜尋

Aho-Corasick 演算法 (1975) 是 Trie + failure link，一次掃描找所有 motif。FIMO (MEME suite)、HOMER 都用此演算法掃描 TFBS。Bowtie 1 也用 Trie 做 short-read 比對。

9. HMM Trellis Graph — gene 預測與 protein family

HMM 的計算是一個 trellis graph：每列是時間 t，每行是 state。Viterbi 演算法本質是這個 graph 上的最短路徑。HMMER3、GENSCAN、Augustus 都用此結構。

Behind every bioinformatics tool lies a critical data-structure choice. Master these, and you'll instantly spot where a new tool's speed comes from.

1. de Bruijn Graph — soul of short-read assembly

SPAdes (Bankevich 2012), Velvet (Zerbino 2008), SOAPdenovo all use de Bruijn graphs: each k-mer (k=21–127) is a node, adjacent k-mers connect. Assembly = find Eulerian path. RAM = #k-mers × node size — why big genomes need TB-class RAM.

2. String Graph / OLC — long-read assembly

Canu (Koren 2017), HiCanu, Flye use Overlap-Layout-Consensus + string graphs: each read is a node, overlaps > 1 kb connect them. Long reads (PacBio HiFi, ONT) suit string graphs better because overlap signal is strong.

3. Hash Table — BLAST & k-mer counting

BLAST hashes the database into 11-mers. KMC3, Jellyfish are k-mer counters built on large hash tables (best versions use minimizers to cut memory).

4. Suffix Tree / Array — theoretical best for sequence search

Suffix Tree (McCreight 1976): O(m) pattern lookup but needs O(n) time + O(n·20) space — 60+ GB for the human genome. Suffix Array (Manber & Myers 1990) is leaner. STAR aligner indexes the genome with a Suffix Array.

5. B-tree / R-tree — BAM index & BED range queries

BAM index .bai uses bin scheme + linear index (B-tree-like), letting samtools view chr1:1000-2000 seek in milliseconds. BEDtools and tabix use R-tree / interval tree for O(log n + k) overlap queries. GenomicRanges (R/Bioconductor) too.

6. Bloom Filter — k-mer existence & sequence retrieval

Cuttlefish 2 uses Bloom filters to reduce k-mer counting memory. BIGSI (Bradley 2019) and COBS use Bloom filters to query PB-scale sequence databases — tiny RAM, controlled false-positive rate.

7. Priority Queue / Heap — Genome Browser & Dijkstra

IGV / JBrowse sort multi-track events via priority queue. HISAT2 graph traversal and Bandage visualization rely on priority queues. Dijkstra on haplotype graphs needs a min-heap.

8. Trie / Aho-Corasick — short-sequence & motif matching

Aho-Corasick (1975) = Trie + failure links, finding all motifs in one pass. FIMO (MEME), HOMER use it for TFBS. Bowtie 1 used a Trie for short-read alignment.

9. HMM Trellis Graph — gene prediction & protein families

HMM computation is a trellis: columns are time t, rows are states. Viterbi is essentially shortest path on this graph. HMMER3, GENSCAN, Augustus all use it.

🎯
記住這個對應表：序列比對 → BWT/FM-Index；組裝 → de Bruijn / string graph；變異註解區間查詢 → interval tree；k-mer 存在性 → Bloom filter；資料庫索引 → B-tree。新工具發表時，先看它用什麼資料結構，就知道它的瓶頸在哪。
Memorize this cheat sheet: alignment → BWT/FM-Index; assembly → de Bruijn / string graph; variant range query → interval tree; k-mer existence → Bloom filter; DB index → B-tree. When a new tool drops, check its data structure first — that tells you the bottleneck.

🌳 結構選擇樹

Q1:
需要 O(1) 索引存取嗎？→ Array / Vector（Python list, NumPy）。Cache 最友善。
Q2:
需要 O(1) key→value 查找？→ Hash Table（Python dict）。但無序、無範圍查詢。
Q3:
需要「有序」 + 「範圍查詢」 + 「O(log n) 操作」？→ 平衡 BST / B-tree（C++ map, SQL index）。
Q4:
頻繁取最小/最大？→ Binary Heap / Priority Queue（Python heapq）。
Q5:
前綴搜尋 / autocomplete？→ Trie / Radix Tree。
Q6:
「是否存在」+ 記憶體有限 + 可接受誤判？→ Bloom Filter（k-mer 存在性、URL 黑名單）。
Q7:
區間 overlap 查詢（基因組區間）？→ Interval Tree / R-tree（BEDtools, tabix）。
Q8:
節點 + 關係（基因網路、社群）？→ Graph (adjacency list)，搭配 NetworkX/igraph。
Q9:
不確定時，選 Array。改寫到別的結構通常不難，過早最佳化是萬惡之源。
Q1:
Need O(1) index access? → Array / Vector (Python list, NumPy). Most cache-friendly.
Q2:
Need O(1) key→value lookup? → Hash Table (Python dict). Unordered, no range queries.
Q3:
Need "ordered" + range queries + O(log n) ops? → Balanced BST / B-tree (C++ map, SQL index).
Q4:
Frequently pop min/max? → Binary Heap / Priority Queue (Python heapq).
Q5:
Prefix search / autocomplete? → Trie / Radix Tree.
Q6:
"Maybe exists" + limited RAM + tolerate false positives? → Bloom Filter (k-mer existence, URL blacklist).
Q7:
Interval-overlap queries (genome ranges)? → Interval Tree / R-tree (BEDtools, tabix).
Q8:
Nodes + relationships (gene networks, social)? → Graph (adjacency list) + NetworkX/igraph.
Q9:
Unsure? Start with Array. Rewriting later is usually easy; premature optimization is the root of all evil.

BAM 檔案的多層資料結構

八-B、BAM 多層資料結構案例

一個 1 TB 的 WGS BAM 檔案，samtools view chr1:1000000-1100000 為何能在 50ms 內回應？背後堆疊了 6 種資料結構：

  1. ① BGZF 壓縮塊（Array of Blocks）：BAM 不是「整檔 gzip」——而是切成多個 64 KB 的 BGZF block，每塊獨立壓縮。關鍵：能隨機跳到任一 block 解壓，不必從頭。
  2. ② Virtual File Offset (64-bit)：每個 record 用一個 64-bit 整數定位：高 48 bit 是 BGZF block 在檔案的位置，低 16 bit 是 block 內 byte offset。這是一種人造的「分層 array index」。
  3. ③ Bin Scheme (Hierarchical Hash)：把參考基因組切成多層 bin：level 0 = 整條 chr，level 1 = 每 512 Mb，level 5 = 每 16 kb。類似 R-tree 但離散化，UCSC binning scheme (Kent 2002 Genome Res) 啟發。
  4. ④ Linear Index (Array)：對每 16 kb window 存「第一個與此 window 重疊的 read 的 virtual offset」。讓查詢能跳過大量空白區域。
  5. ⑤ Chunk List (Linked List per Bin)：每個 bin 記錄屬於它的所有「virtual offset 區間」(chunks)。查詢時把 query range 對應的 bin 與 linear index 結果合併、deduplicate。
  6. ⑥ Memory-mapped File (OS-level)：samtools 可選擇用 mmap，由 OS 管理 page cache（Ch 6 OS 章節！）。熱常用區域自動快取在 RAM，重複查詢無 disk IO。

查詢流程：① 解析 chr1:1000000-1100000；② 用 bin scheme 找出涵蓋此區間的 bin 集合（最多 ~6 個）；③ 用 linear index 跳過無 read 的 chunk；④ 用每 bin 的 chunk list 收集候選 virtual offsets；⑤ jump 到對應 BGZF block 解壓；⑥ 過濾出真正落在 query range 的 read。

結果：1 TB BAM 的隨機區間查詢只需讀 1-5 個 BGZF block (約 1 MB) → 50ms 完成。沒有 .bai 索引就要 sequential scan 1 TB → 10+ 分鐘。差距 10,000×。

啟示：「分層 + 多種資料結構組合」是處理 TB-PB 級科學資料的唯一辦法。BAM 1.6 規格 (Heng Li 2009) 至今 17 年仍主導 NGS——這是資料結構工程的巔峰之作。CRAM (2014, Hsi-Yang Fritz et al.) 進一步把壓縮率提高 30-50%，但索引架構幾乎不變。

A 1 TB WGS BAM file — why does samtools view chr1:1000000-1100000 respond in 50 ms? Behind it lies a stack of 6 data structures:

  1. ① BGZF Compressed Blocks (Array of Blocks): BAM isn't whole-file gzip — it's split into 64-KB BGZF blocks, each compressed independently. Key: random-jump to any block without reading from start.
  2. ② Virtual File Offset (64-bit): each record's position is a 64-bit integer — high 48 bits = BGZF block's file offset, low 16 bits = byte offset inside the block. An engineered "layered array index."
  3. ③ Bin Scheme (Hierarchical Hash): divide the reference into multi-level bins — level 0 = whole chromosome, level 1 = each 512 Mb, level 5 = each 16 kb. R-tree-like but discretized; inspired by UCSC binning (Kent 2002 Genome Res).
  4. ④ Linear Index (Array): for every 16-kb window, store the "virtual offset of the first read overlapping it" — lets queries skip huge empty regions.
  5. ⑤ Chunk List (Linked List per Bin): each bin records all "virtual offset intervals" (chunks) belonging to it. Queries merge and deduplicate the bin's chunks with the linear-index hits.
  6. ⑥ Memory-mapped File (OS level): samtools can use mmap; the OS manages page cache (recall Ch 6 OS!). Hot regions get auto-cached in RAM, repeat queries skip disk I/O.

Query flow: (1) parse chr1:1000000-1100000; (2) bin scheme finds ~6 covering bins; (3) linear index skips empty chunks; (4) chunk lists collect candidate virtual offsets; (5) jump to BGZF blocks and decompress; (6) filter to reads truly inside the query range.

Result: a random range query on 1 TB BAM reads only 1-5 BGZF blocks (~1 MB) → 50 ms. Without .bai it would be a sequential scan of 1 TB → 10+ minutes. 10,000× difference.

Takeaway: "Layered + multiple-data-structure composition" is the only way to handle TB-PB-scale scientific data. BAM 1.6 (Heng Li 2009) has dominated NGS for 17 years — a pinnacle of data-structure engineering. CRAM (Hsi-Yang Fritz et al. 2014) improves compression 30-50% with nearly the same indexing architecture.

常見誤解

九、常見誤解

❌ 「Linked List 比 Array 快」

大部分情況反過來。Array 的 cache locality 大勝——同一個 cache line (64 byte) 能讀進 16 個 int。Linked List 每個節點隨機 malloc，CPU cache miss 連連。Bjarne Stroustrup 著名演講「為何 vector 永遠贏 list」(2012) 證明：對 100,000 個元素的中間插入，vector 仍快過 linked list 5×。

Usually the opposite. Array's cache locality wins — one 64-byte cache line holds 16 ints. Linked-list nodes are scattered, causing cache misses. Stroustrup's famous talk "Why vector beats list" (2012) showed: even for middle-inserting 100,000 elements, vector beats linked list 5×.

❌ 「Hash Table 永遠 O(1)」

那是「平均」case。最壞 O(n)：若所有 key hash 到同一 bucket（攻擊者刻意製造），dict 變 linked list。2011 年 hash flooding 攻擊讓 PHP/Java/Python 集體當機。Python 3.3+ 預設 SipHash + random seed 對抗此攻擊。

That's the average. Worst case O(n): if all keys hash to one bucket (attacker-crafted), the dict becomes a linked list. The 2011 hash-flooding attacks crashed PHP/Java/Python sites en masse. Python 3.3+ defaults to SipHash + random seed to defend.

❌ 「BST 自動平衡」

沒有「自動」這回事。普通 BST 不平衡，最壞退化成 linked list O(n)。必須是 AVL、RB Tree、Splay Tree、Treap 等「自平衡」變種。Python 沒有內建 BST，要用 sortedcontainers。

"Automatic" is a myth. Plain BST is not balanced — worst case it degenerates to a linked list O(n). You need AVL, RB Tree, Splay Tree, Treap, etc. Python has no built-in BST; use sortedcontainers.

❌ 「Python list 是 linked list」

Python list 內部是 動態陣列 (dynamic array)——連續記憶體 + 翻倍擴容。所以 list[i] 是 O(1)，list.append() 均攤 O(1)。但 list.insert(0, x) 是 O(n) — 用 collections.deque。

Python list is a dynamic array — contiguous memory + doubling. So list[i] is O(1), list.append() amortized O(1). But list.insert(0, x) is O(n) — use collections.deque.

五大進階樹結構

九-A、五大進階樹

① Red-Black Tree (RB Tree)

1972 Bayer 提出 「symmetric binary B-trees」，1978 Guibas & Sedgewick 重新命名為 RB Tree。每節點塗紅或黑，五條規則保證高度 ≤ 2·log₂(n+1)。比 AVL 寬鬆 → 插入旋轉次數少 → 實務 50% 應用首選。Linux CFS 排程器、C++ std::map、Java TreeMap、Python sortedcontainers 都是 RB Tree。

1972 Bayer proposed "symmetric binary B-trees"; 1978 Guibas & Sedgewick renamed it RB Tree. Each node is red or black; 5 rules cap height at 2·log₂(n+1). Looser than AVL → fewer rotations → ~50% of practical use. Linux CFS scheduler, C++ std::map, Java TreeMap, Python sortedcontainers all use RB Tree.

② B+ Tree

B-tree 的延伸：只有葉節點存資料，內部節點只存索引；葉節點用 linked list 串起來方便 range scan。2026 年所有主流 RDBMS（PostgreSQL、MySQL InnoDB、Oracle、SQL Server）的 primary index 都是 B+ Tree。為何？fanout 大（一節點 100+ key）→ 高度極矮 (3-4 層裝 10 億筆) → 每次磁碟讀取最少。

B-tree extension: only leaves store data; internal nodes hold indices only; leaves chained as a linked list for range scans. By 2026 every major RDBMS (PostgreSQL, MySQL InnoDB, Oracle, SQL Server) uses B+ Tree for its primary index. Why? high fanout (100+ keys/node) → tiny height (3-4 levels for 1B rows) → minimal disk reads.

③ Skip List

1989 William Pugh 在 Maryland 大學發明。機率資料結構：多層 linked list 疊在一起，每層約上一層的一半節點。期望 O(log n)，最壞 O(n)（極罕見）。實作比 RB Tree 簡單 50%，效能相當。Redis 的 sorted set (ZSET)、LevelDB、RocksDB、Apache HBase 全用 Skip List。

1989 William Pugh at Maryland. Probabilistic structure: stacked linked lists, each layer ~half of the one below. Expected O(log n), worst O(n) (rare). Half the code of RB Tree with similar performance. Redis sorted sets (ZSET), LevelDB, RocksDB, Apache HBase all use Skip List.

④ LSM Tree (Log-Structured Merge)

1996 Patrick O'Neil 提出。專為寫密集設計：新資料先寫到 memtable，定期 flush 到 sorted file (SSTable)，再背景 merge。寫入 O(1)（不需找位置），讀取要查多層 → 用 Bloom filter 加速。Google Bigtable、HBase、Cassandra、LevelDB、RocksDB、TiDB 的底層都是 LSM Tree。對 NGS 中間 BAM/VCF 寫入也有應用。

1996 Patrick O'Neil. Designed for write-heavy workloads: new data goes to a memtable, periodically flushed to sorted files (SSTable), then merged in the background. Writes O(1) (no seek), reads check multiple levels — Bloom filters speed them up. Google Bigtable, HBase, Cassandra, LevelDB, RocksDB, TiDB all use LSM Tree. NGS intermediate BAM/VCF writes use similar ideas.

⑤ Splay Tree (自伸展樹)

1985 Sleator & Tarjan (Tarjan 是圖靈獎)。無平衡規則，但每次存取後把該節點「splay」到根。均攤 O(log n)，且符合「最近用到的最快」(locality of reference) 性質——cache-friendly。實作極簡，但最壞單次操作仍可 O(n)。某些版本 Linux kernel、Windows NT cache 曾用。

1985 Sleator & Tarjan (Tarjan a Turing laureate). No balance rules, but every access "splays" the node to the root. Amortized O(log n), with strong locality of reference — cache-friendly. Tiny implementation, but worst-case op can still be O(n). Used in some Linux kernel paths and old Windows NT caches.

⑥ FM-Index (Full-text Minute-space)

2000 Ferragina & Manzini。基於 BWT 的全文索引，能在 壓縮空間 內做 O(m) pattern 搜尋。BWA、Bowtie2 用 FM-Index 把 30 億 bp 的人類基因組塞進 3 GB 記憶體並支援 O(read_length) 比對——這是 NGS 革命的關鍵資料結構。

2000 Ferragina & Manzini. A full-text index built on BWT that supports O(m) pattern search in compressed space. BWA, Bowtie2 use FM-Index to fit the 3 Gbp human genome into 3 GB of RAM and support O(read_length) alignment — the data structure that enabled the NGS revolution.

三大進階 Hash

九-B、三大進階 Hash

① Cuckoo Hashing

2001 Pagh & Rodler 發明。用 兩個 hash function：若 h₁ 與 h₂ 兩 bucket 都被占了，「踢掉」其中一個讓它去另一個位置（cuckoo 杜鵑鳥）。查詢保證 O(1) worst case（最多檢查 2 個 bucket）！缺點：load factor > 50% 容易陷入迴圈，需 rehash。Memcached、近年的 high-perf hash table。

2001 Pagh & Rodler. Use two hash functions: if both h₁ and h₂ buckets are full, "evict" one (like a cuckoo) to its alternate spot. Guaranteed O(1) worst-case lookup (at most 2 buckets checked)! Downside: load factor > 50% risks cycles, forcing rehash. Used in Memcached and modern high-perf hash tables.

② Robin Hood Hashing

1985 Pedro Celis 在 Waterloo 提出。Open addressing 的變體：插入時若新元素的 「探測距離」 (probe distance) 比現有的長，就「搶」現有位置（「劫富濟貧」）。大幅降低 variance、查詢更穩定。Rust 的 std::HashMap、ClickHouse、Tableau 都用。

1985 Pedro Celis (Waterloo). Open addressing variant: on insert, if the new element's probe distance exceeds the current occupant's, "steal" the slot ("rob from the rich"). Drastically lowers variance, more predictable lookups. Rust std::HashMap, ClickHouse, Tableau use it.

③ Consistent Hashing

1997 MIT Karger et al. 為 Akamai CDN 發明。把 hash space 想成一個環，節點與 key 都映射到環上，key 由「下一個順時針」節點負責。新增/移除節點時，只有 1/N 的 key 需要搬移，而非全部 rehash。Cassandra、DynamoDB、CDN、分散式快取 全靠它。

1997 MIT Karger et al. for Akamai CDN. Map hash space to a ring; both nodes and keys map onto the ring; each key is owned by the "next clockwise" node. Adding/removing a node moves only 1/N of keys, no full rehash. Cassandra, DynamoDB, CDNs, distributed caches all rely on this.

④ Count-Min Sketch / Count Sketch

2004 Cormode & Muthukrishnan。probabilistic frequency estimator：用 d 個 hash function 將每筆事件分到 w 個 bucket，計次後取 min。記憶體 O(d·w)，遠小於精確計數。k-mer 頻率估算、網路流量計、推特即時 trending都用。誤差有上界保證。

2004 Cormode & Muthukrishnan. Probabilistic frequency estimator: d hash functions place each event into w buckets; counts are taken as the min across rows. Memory O(d·w), far less than exact counting. Used in k-mer frequency estimation, network telemetry, Twitter live trending. Error bounds are provable.

持久 / Persistent 結構

九-C、Persistent 資料結構

「Persistent」此處不是「存到磁碟」，而是「修改後舊版本仍可用」。每次「修改」其實是建立一個新版本，與舊版本共享大部分結構（structural sharing）。

關鍵應用：

  • Git 的 object store：commit 不修改舊資料，只加新 blob/tree。所以你可以 checkout 任何歷史版本。本質就是 persistent Merkle tree。
  • Clojure 的核心結構：list、vector、map、set 全部 persistent。底層用 Hash Array Mapped Trie (HAMT)，Phil Bagwell 2001 發明。
  • 函數式語言 (Haskell, Erlang, F#)：所有資料預設 immutable。
  • React / Redux 的狀態管理：用 immutable.js / Immer 確保時間旅行 debug。
  • 區塊鏈 (Bitcoin, Ethereum)：UTXO + Merkle Patricia Trie 都是 persistent。

對生資的潛在用途：① 版本化基因組註解（每次更新 Ensembl 注解只加 diff 不重寫）；② 系統發生樹的編輯歷史；③ 共同分析中追蹤每個分析步驟對細胞分群的影響。Bioconductor 的 SummarizedExperiment 雖非 strictly persistent，但 S4 slot 修改 = 複製新物件，類似精神。

"Persistent" here does not mean "saved to disk" — it means "old versions remain accessible after modification." Every "edit" creates a new version that shares most structure with the old (structural sharing).

Key applications:

  • Git's object store: commits don't modify old data, only add new blobs/trees. That's why you can check out any historical version. It is essentially a persistent Merkle tree.
  • Clojure's core structures: list/vector/map/set all persistent. Backed by Hash Array Mapped Trie (HAMT) — Phil Bagwell 2001.
  • Functional languages (Haskell, Erlang, F#): immutable by default.
  • React/Redux state: immutable.js / Immer for time-travel debugging.
  • Blockchains (Bitcoin, Ethereum): UTXO + Merkle Patricia Trie are persistent.

Potential bioinformatics uses: (1) versioned genome annotations (Ensembl updates as diffs); (2) phylogenetic-tree edit history; (3) tracking how each analysis step alters cell clustering. Bioconductor's SummarizedExperiment isn't strictly persistent, but S4 slot edits do return new objects — kindred spirit.

空間索引 R-tree / R*-tree

九-D、R-tree 空間索引

當你問：「在 chr1:1,000,000-1,100,000 區間裡有哪些 SNP / gene / peak？」—— 用線性掃描要 O(n)，但用 R-tree 是 O(log n + k)。

R-tree (Guttman 1984) 把每個物件（點、區間、長方形）裝進 最小包圍盒 (MBR, Minimum Bounding Rectangle)，然後遞迴把 MBR 群組成更大的 MBR。查詢時剪掉所有 MBR 與 query 不交的子樹。

R*-tree (1990) 是改進版，插入時嘗試重新插入相鄰節點以最小化 overlap，2026 仍是 PostGIS、SQLite SpatiaLite 的預設。

生資對應的「區間樹 (Interval Tree)」：

  • BEDtools (Quinlan & Hall 2010, Bioinformatics)：intersect / merge / closest，內部即 interval tree。
  • tabix (Li 2011, Bioinformatics)：在壓縮 BED/GFF/VCF 上做 O(log n) 區間查詢，BAM .bai 的兄弟。
  • GenomicRanges (R/Bioconductor)：findOverlaps, countOverlaps 是 interval tree。
  • pyranges (Stovner 2020)：Python 的 GenomicRanges 對應品，比 pybedtools 快 100×。
  • UCSC Genome Browser 的 binning scheme = 多層 interval tree。

哲學啟示：基因組座標是「1D 空間」，所以 1D R-tree (interval tree) 就夠用；但若做空間轉錄組 (Visium、MERFISH) 的「組織切片 2D」，2D R-tree (PostGIS) 才合適。10x Visium HD 2024 起就用空間索引加速。

When you ask: "Which SNPs / genes / peaks lie in chr1:1,000,000-1,100,000?" — linear scan is O(n); with an R-tree, it's O(log n + k).

R-tree (Guttman 1984) wraps each object (point, interval, rectangle) in a Minimum Bounding Rectangle (MBR), then recursively groups MBRs. Queries prune any subtree whose MBR doesn't intersect.

R*-tree (1990) is an improvement that re-inserts nearby nodes on insertion to minimize overlap; still the default in PostGIS and SQLite SpatiaLite in 2026.

Bioinformatics "interval tree" cousins:

  • BEDtools (Quinlan & Hall 2010, Bioinformatics): intersect / merge / closest — internally an interval tree.
  • tabix (Li 2011, Bioinformatics): O(log n) range queries on compressed BED/GFF/VCF; cousin of BAM .bai.
  • GenomicRanges (R/Bioconductor): findOverlaps, countOverlaps — interval tree.
  • pyranges (Stovner 2020): Python's GenomicRanges, 100× faster than pybedtools.
  • UCSC Genome Browser binning scheme = multi-level interval tree.

Takeaway: Genomic coordinates are "1D space," so a 1D R-tree (interval tree) suffices; but for spatial transcriptomics (Visium, MERFISH) the "tissue slice 2D" needs a 2D R-tree (PostGIS). 10x Visium HD (2024) already uses spatial indices for acceleration.

💭 延伸思考

十、延伸思考

  1. 量子資料結構是什麼？量子位元的 superposition 可以同時儲存多個狀態。量子隨機存取記憶體 (QRAM) 可在 O(log n) 查找 n 個 entry——但目前還停在理論。對生物資訊的潛在影響：能否用量子 Hash 同時查詢整個 GenBank？
  2. What are quantum data structures? Qubit superposition stores multiple states at once. Quantum RAM (QRAM) could look up n entries in O(log n) — but it's still theoretical. Potential impact on bioinformatics: could a quantum hash query all of GenBank at once?
  3. Persistent (不可變) 資料結構的優雅之處？Git 的 object store 是 persistent Merkle tree——每次 commit 不修改舊資料，只加新節點。所以你可以 checkout 任何歷史版本而無資料遺失。Clojure 的核心資料結構全部 persistent。函數式設計的核心思想之一。
  4. The elegance of persistent (immutable) data structures? Git's object store is a persistent Merkle tree — each commit doesn't modify old data, only adds new nodes. That's why you can check out any historical version without loss. Clojure's core structures are all persistent. A pillar of functional design.
  5. 為何 cache-aware 的 B-tree 仍勝過理論最佳的 RB Tree？RB Tree 是 O(log₂ n)，B-tree 是 O(log_B n)，B (節點大小) = 100~1000。實務上 B-tree 比 RB Tree 快 10×，因為 disk/cache 每次讀都是 4 KB / 64 byte 塊。真實電腦不是 RAM 模型，是 memory hierarchy。
  6. Why does cache-aware B-tree beat the "theoretically optimal" RB Tree? RB Tree is O(log₂ n), B-tree is O(log_B n) with B (node size) = 100–1000. In practice B-tree is 10× faster than RB Tree because disk/cache reads come in 4 KB / 64 B blocks. Real computers aren't the RAM model — they're a memory hierarchy.
