56 年的軟體危機

從 Garmisch 1968 到 Crowdstrike 2024

1968 年 10 月，58 位電腦科學家在德國 Garmisch 召開 NATO Software Engineering Conference。會中 Edsger Dijkstra 首次提出「軟體危機 (software crisis)」一詞——當時 IBM OS/360 專案延遲 3 年、超支 5 倍、bug 上萬個。會議結論：軟體開發需要像「橋樑工程」一樣的紀律——於是 「Software Engineering」 一詞誕生。

56 年後的 2024 年 7 月 19 日：資安公司 CrowdStrike 推送一個小小的 Falcon sensor 設定檔更新，因為一個 沒做完整測試 的 null pointer，全球 850 萬台 Windows 機器 同時藍屏。航班停飛、銀行癱瘓、醫院手術延期、911 服務中斷。單次經濟損失估計 100 億美金，是史上最嚴重的單一軟體故障。

1968 → 2024，技術已突飛猛進——但軟體危機從未消失。這正是軟體工程存在的理由：版本控制、測試、CI/CD、code review、漸進式部署 (canary)——每一項都是用血淚換來的紀律。

這一章不只教你 Git 怎麼用，更要回答：為什麼 nf-core 對 bioinformatics pipeline 訂出 30 條規範？Bioconductor 為何要 R CMD check？Snakemake 與 Nextflow 為何能在你的論文被引用？

October 1968 — 58 computer scientists met at the NATO Software Engineering Conference in Garmisch, Germany. Edsger Dijkstra coined "software crisis" there: IBM OS/360 was 3 years late, 5× over budget, with tens of thousands of bugs. The conclusion: software development needed bridge-engineering discipline — and "software engineering" was born as a term.

July 19, 2024 — 56 years later: security firm CrowdStrike pushed a small Falcon sensor config update. A poorly-tested null pointer bluescreened 8.5 million Windows machines worldwide. Flights grounded, banks frozen, hospital surgeries delayed, 911 outages. Estimated $10 billion economic loss — the worst single software failure in history.

1968 → 2024 — technology has exploded, but the software crisis never went away. That's exactly why software engineering exists: version control, tests, CI/CD, code review, canary deploys — each is a discipline paid for in blood.

This chapter teaches more than "how to use Git." It answers: why does nf-core have 30 rules for bioinformatics pipelines? Why does Bioconductor require R CMD check? Why do Snakemake and Nextflow show up in your paper citations?

💡
核心觀念：軟體工程 ≠ 寫程式。寫程式是「讓電腦做事」；軟體工程是「讓一個 5 人團隊在 3 年後仍能維護這份程式碼」。版本控制、測試、文件、CI/CD 都是為了「未來的你」與「同事」而存在。 Core idea: Software engineering ≠ programming. Programming is "make the computer do something"; software engineering is "make sure a 5-person team can still maintain this code 3 years later." Version control, tests, docs, CI/CD all exist for your future self and your teammates.

Git, TDD, SOLID

三、深入剖析：Git, TDD, SOLID

3.1 Git 內部的四種物件

Git 不是「diff 工具」，它是內容定址 (content-addressable) 的物件資料庫，所有東西用 SHA-1 (新版 SHA-256) 雜湊定址。四種物件：

  • blob：檔案內容（無檔名！）。同內容只存一份。
  • tree：目錄結構（名稱 + 權限 + blob/tree 指標）。
  • commit：時間 + 作者 + 訊息 + tree pointer + parent commit pointer。
  • tag：給某 commit 一個「人類友善」名稱。

所以 Git 的「歷史」本質是一個 DAG (Directed Acyclic Graph) of commits——這正是 Ch 11 學的圖結構！branch 只是「指向某 commit 的可變指標」。

Git is not a "diff tool" — it's a content-addressable object database, where everything is keyed by SHA-1 (now SHA-256). Four object types:

  • blob: file content (no filename!). Same content stored once.
  • tree: directory (names + permissions + pointers to blobs/trees).
  • commit: time + author + message + tree pointer + parent commit pointer.
  • tag: human-friendly name for a commit.

So Git history is essentially a DAG (Directed Acyclic Graph) of commits — exactly the graph structure from Ch 11! A branch is just a "mutable pointer to a commit."

3.2 Merge vs Rebase：兩種歷史哲學

Merge：建立一個新的「merge commit」連結兩條分支，保留完整歷史。優點：真實；缺點：歷史像盤義大利麵。

Rebase：把你的 commit「搬到」目標 branch 的最新點之後，歷史變直線。優點：乾淨；缺點：不可對 public branch 做 rebase（會改寫他人 commit）。

原則：個人 feature branch → rebase；共享 branch → merge。

Merge: creates a "merge commit" linking two branches, preserving full history. Pro: true; con: history looks like spaghetti.

Rebase: replays your commits on top of the target branch's tip, making history linear. Pro: clean; con: never rebase a public branch (rewrites others' commits).

Rule: personal feature branch → rebase; shared branch → merge.

3.3 測試金字塔

Mike Cohn (2009) 的「測試金字塔」：

  • 底層（70%）：Unit tests——測單一函式、毫秒級、ms-level。
  • 中層（20%）：Integration tests——多個模組互動、秒級。
  • 頂層（10%）：E2E tests——完整流程（瀏覽器點擊）、分鐘級。

反模式：「ice cream cone」——上多下少，導致測試慢、修起來貴。TDD (Test-Driven Development)：先寫 failing test → 寫最少程式碼讓它過 → refactor。

Mike Cohn (2009)'s testing pyramid:

  • Base (70%): Unit tests — single functions, milliseconds.
  • Middle (20%): Integration tests — multi-module, seconds.
  • Top (10%): E2E tests — full flow (browser clicks), minutes.

Anti-pattern: "ice cream cone" — heavy at top, slow and expensive. TDD (Test-Driven Development): write failing test → write minimum code to pass → refactor.

3.4 SOLID 五大原則

Robert C. Martin (Uncle Bob) 2000 年提出，OOP 設計的五大圭臬：

  • Single Responsibility — 一個 class 只做一件事。
  • Open/Closed — 對擴充開放、對修改封閉。
  • Liskov Substitution — 子類能完全替代父類。
  • Interface Segregation — 介面要小而專。
  • Dependency Inversion — 依賴抽象，不依賴具體。

Robert C. Martin (Uncle Bob) coined SOLID in 2000 — five OOP design pillars:

  • Single Responsibility — one class, one reason to change.
  • Open/Closed — open to extension, closed to modification.
  • Liskov Substitution — subclasses must substitute for parents.
  • Interface Segregation — small, focused interfaces.
  • Dependency Inversion — depend on abstractions, not concretions.
六個改變產業的故事

四、六個改變軟體業的故事

① Garmisch 1968 — 軟體危機誕生

NATO 召開首屆軟體工程會議。IBM OS/360 是「燃燒中的反例」——延遲 3 年、上千 bug。Fred Brooks 後來寫 The Mythical Man-Month (1975)，提出「加更多人到落後專案只會更慢」(Brooks's Law)、「沒有銀彈 (No Silver Bullet)」——這兩條至今 100% 成立。

NATO held the first software engineering conference. IBM OS/360 was the "burning counter-example" — 3 years late, thousands of bugs. Fred Brooks later wrote The Mythical Man-Month (1975), giving us "adding people to a late project makes it later" (Brooks's Law) and "No Silver Bullet" — both 100% still true today.

② Agile Manifesto (2001) — 17 人在雪山

2001 年 2 月，17 位軟體界人物（Martin Fowler、Kent Beck、Ward Cunningham、Robert Martin...）在 Utah Snowbird 度假村開會，寫下 4 條核心價值與 12 條原則。Agile Manifesto 從此改變產業。它的核心：「個人與互動」優於「流程與工具」。

February 2001, 17 luminaries (Martin Fowler, Kent Beck, Ward Cunningham, Robert Martin...) met at Snowbird, Utah, and wrote 4 core values + 12 principles. The Agile Manifesto reshaped the industry. Core: "individuals and interactions" over "processes and tools."

③ Git (2005) — 兩週寫成

2005 年 4 月，Linux kernel 與商業 SCM BitKeeper 鬧翻。Linus Torvalds 在 兩週內 寫出 Git，從此 Linux 用 Git 至今。設計核心：① 分散式（每人都有完整 history）、② 內容定址、③ 快（C 寫的）。2026 年 Git 是 95%+ 開源專案的版本控制標準。

April 2005 — fight between Linux kernel and commercial SCM BitKeeper. Linus Torvalds wrote Git in two weeks; Linux has used it ever since. Design: (1) distributed (every clone has full history), (2) content-addressable, (3) fast (C). By 2026 Git is the version control standard for 95%+ of open-source.

④ GitHub (2008) — 開源民主化

Tom Preston-Werner、Chris Wanstrath、PJ Hyett 三人在舊金山創業，把 Git 變成「社交平台」。Pull Request、Issue tracker、forking culture——把開源從「論壇 + email patch」變成 click-to-contribute。2018 年 Microsoft 以 75 億美金收購。2026 年有超過 1.2 億開發者。

Tom Preston-Werner, Chris Wanstrath, PJ Hyett founded GitHub in SF, turning Git into a social platform. Pull Requests, Issue trackers, forking culture — open source went from "forum + email patch" to click-to-contribute. Microsoft acquired it for $7.5B in 2018. 120M+ developers by 2026.

⑤ Heartbleed (2014) — 兩年沒人發現

2014 年 4 月，Google 與 Codenomicon 同時發現 OpenSSL 一個 2 年前 commit 的 bug——攻擊者能讀任意 64 KB 記憶體，包括 password、private key。影響全球 17% HTTPS 網站。教訓：① 開源 ≠ 安全 (沒人 review)、② 加入 fuzz testing、③ OSS-Fuzz 計畫誕生。

April 2014, Google + Codenomicon simultaneously discovered an OpenSSL bug committed 2 years earlier — attackers could read arbitrary 64 KB of memory, including passwords and private keys. Affected 17% of HTTPS sites worldwide. Lessons: (1) open source ≠ secure (nobody was reviewing), (2) add fuzz testing, (3) the OSS-Fuzz project was born.

⑥ Crowdstrike (2024) — 一個 null pointer 850 萬台

2024-07-19 凌晨，CrowdStrike Falcon Sensor 推送「Channel File 291」更新到全球所有客戶。因 staged rollout 缺失 + null pointer 未測試，850 萬台 Windows 同時 BSOD。航空、銀行、醫療癱瘓 8 小時。教訓：① canary rollout 是命；② kernel-mode 軟體須極嚴測試；③ 一個 bug 可能等於 100 億美金。

July 19, 2024 — CrowdStrike Falcon Sensor pushed "Channel File 291" globally. No staged rollout + untested null pointer bluescreened 8.5 million Windows machines. Airlines, banks, hospitals frozen for 8 hours. Lessons: (1) canary rollouts save lives; (2) kernel-mode code needs extreme testing; (3) one bug can equal $10 billion.

🧬 給生物資訊學家

六、🧬 生資連結：可重現研究的軟體工程

2026 年的 bioinformatics，可重現性 (reproducibility) 已是論文發表的硬性要求。許多頂級期刊（Nature 系列、Cell、Bioinformatics）要求 (1) 程式碼公開、(2) 容器化或環境凍結、(3) 工作流程明確。這些都是軟體工程的核心。

1. Bioconductor 套件開發規範

Bioconductor 對提交的 R 套件要求極嚴：① R CMD check 必須通過、無 error/warning；② 必須附 vignette（含跑得通的範例）；③ 必須有 unit tests (testthat)；④ S4 class 強型別優於 S3；⑤ 每 6 個月隨 R 升級。結果：Bioconductor 2,200+ 套件比 CRAN 更穩定可信。

2. nf-core 規範 (Nextflow pipeline)

nf-core 是 Nextflow pipeline 的共通規範 + 100+ 認證 pipeline (rnaseq, sarek, atacseq...)。要求：① schema (nextflow_schema.json) 描述參數；② test config 用小資料集跑 CI；③ GitHub Actions 每 PR 自動 lint + test；④ Conda + Docker + Singularity 三選一容器；⑤ DOI 自動產生 via Zenodo。

3. Snakemake 與軟體工程整合

Snakemake (Köster 2012, 2021 Bioinformatics update) 把 workflow 寫成 Python 語法。整合：① DAG 自動推導依賴；② Conda env per rule (隔離依賴)；③ Singularity 容器；④ --report 自動產 HTML report；⑤ --cluster 一鍵跑 SLURM/PBS。

4. Git LFS 與大檔處理

FASTQ、BAM、CRAM 不能直接 commit 進 Git（單檔可能 GB 級，Git 會崩潰）。Git LFS (Large File Storage)：把大檔存在外部，Git 只記 pointer。但更好的做法：用 DVC 或 nf-core 慣例——資料留在 S3/iRODS/SRA，pipeline 才在 Git。

5. GitHub Actions 跑 bioinformatics CI

每個 commit 自動：① pytest 或 testthat 跑 unit tests；② nextflow run -profile test 跑 mini pipeline；③ R CMD check 檢查 Bioconductor 規範；④ linting (snakefmt / Black / lintr)；⑤ build Docker image push 到 ghcr.io。每月可省 100+ 小時手動測試。

6. BioContainers 與 Bioconda

Bioconda 收錄 8,000+ bioinformatics 套件，每個套件 自動產生 Docker image 推到 BioContainers 與 quay.io。一行 conda install -c bioconda samtools 或 docker pull biocontainers/samtools 就能用——這是現代生資工具的事實標準。

7. FAIR 原則 + 資料管理計畫

2016 年 Wilkinson et al. (Nature Sci Data) 提出 FAIR：Findable, Accessible, Interoperable, Reusable。2023 年 NIH 推行 DMS Policy，所有 grant 申請必須有資料管理計畫。2026 起 NSF、Wellcome Trust、EU Horizon 全面跟進——這是軟體工程進入「公共政策」。

8. nf-core / Snakemake workflows / Galaxy 三足鼎立

Nextflow + nf-core：生產環境、雲端、跨機構協作首選。Snakemake：個別實驗室、Python 學者社群。Galaxy：web UI、教學與無 CLI 經驗使用者。共同特徵：DAG-based workflow + reproducibility + container 整合。

By 2026, reproducibility is a publication requirement in bioinformatics. Top journals (Nature family, Cell, Bioinformatics) require (1) public code, (2) containerization or environment pinning, (3) explicit workflows. All software-engineering essentials.

1. Bioconductor package development

Bioconductor rules for R packages: (1) R CMD check must pass with no errors/warnings; (2) ships a vignette with runnable examples; (3) unit tests (testthat); (4) prefer S4 classes over S3; (5) re-released every 6 months with R. Result: 2,200+ packages more stable and trustworthy than CRAN.

2. nf-core (Nextflow pipelines)

nf-core = Nextflow pipeline conventions + 100+ certified pipelines (rnaseq, sarek, atacseq...). Requires: (1) schema (nextflow_schema.json); (2) test config with tiny CI data; (3) GitHub Actions lint+test every PR; (4) Conda + Docker + Singularity options; (5) DOI auto-generated via Zenodo.

3. Snakemake + software engineering

Snakemake (Köster 2012, 2021 Bioinformatics update) writes workflows in Python syntax. Features: (1) DAG auto-derived; (2) Conda env per rule; (3) Singularity support; (4) --report auto-HTML; (5) --cluster one-line SLURM/PBS submission.

4. Git LFS & large files

FASTQ, BAM, CRAM cannot be committed to Git directly (multi-GB files crash Git). Git LFS: stores big files externally, Git keeps pointers. Even better: use DVC or the nf-core convention — data stays in S3/iRODS/SRA, only the pipeline lives in Git.

5. GitHub Actions for bioinformatics CI

Each commit auto-runs: (1) pytest or testthat unit tests; (2) nextflow run -profile test mini pipeline; (3) R CMD check for Bioconductor; (4) linting (snakefmt / Black / lintr); (5) build Docker image push to ghcr.io. Saves 100+ hours/month of manual testing.

6. BioContainers & Bioconda

Bioconda hosts 8,000+ bio packages; each auto-builds a Docker image pushed to BioContainers + quay.io. One-liner conda install -c bioconda samtools or docker pull biocontainers/samtools — the de facto standard for modern bio tooling.

7. FAIR principles + data management

Wilkinson et al. 2016 (Nature Sci Data) coined FAIR: Findable, Accessible, Interoperable, Reusable. In 2023 NIH adopted the DMS Policy — every grant needs a data management plan. NSF, Wellcome, EU Horizon followed by 2026 — software engineering became public policy.

8. Three workflow ecosystems

Nextflow + nf-core: production, cloud, multi-institution. Snakemake: individual labs, Python community. Galaxy: web UI, education, CLI-free users. Common: DAG-based + reproducible + containerized.

給生資新人的最低軟體工程清單：① 用 Git + GitHub (不是私人雲端硬碟)；② 寫 requirements.txt 或 environment.yml 凍結環境；③ 對主函式至少寫 3 個 pytest 或 testthat；④ pipeline 用 Snakemake / Nextflow 不要寫 shell 大雜燴；⑤ 用 Docker 或 Singularity 容器；⑥ 在 README 寫清楚怎麼重現。這 6 條是發 Nature 子刊的入場券。
Minimum software-engineering checklist for bio newcomers: (1) Git + GitHub (not personal cloud drives); (2) pin environment with requirements.txt or environment.yml; (3) at least 3 pytest or testthat tests for core functions; (4) pipelines in Snakemake / Nextflow, not shell spaghetti; (5) containerize with Docker or Singularity; (6) reproducibility instructions in the README. These 6 are your admission ticket to Nature-family journals.

Q1:
Merge or Rebase? → Tidying personal feature branch → rebase; merging into shared main → merge. Never rebase a public branch.
Q2:
Is TDD right for bioinformatics? → For core logic (parsers, variant callers, stats), yes; for EDA / exploration, no. Mix the two.
Q3:
Nextflow or Snakemake? → Big team / cloud / multi-org → Nextflow + nf-core; single lab / Python preference → Snakemake; web UI / teaching → Galaxy.

Q6:
New feature — push directly or PR first? → Any change >50 lines → PR + review. Same for bugfixes.
Q7:
CI failing — what now? → Never force-merge. Fix until green. Merging a red CI is the start of team hell.

# bio_utils.py
def reverse_complement(seq: str) -> str:
    """Return reverse-complement of a DNA string."""
    comp = str.maketrans('ACGTacgt', 'TGCAtgca')
    return seq.translate(comp)[::-1]

nf-core 的軟體工程治理

八-B、nf-core 治理案例

nf-core (Ewels et al. 2020 Nature Biotechnology) 是 bioinformatics 史上最成功的開源治理案例——3000+ 貢獻者、100+ certified pipeline、用於數千個論文。讓我們拆解它如何把這一切「軟體工程化」：

  1. ① Cookiecutter Template：一個指令 nf-core create 就生出完整 pipeline skeleton——包含 main.nf、modules、subworkflows、tests、docs、CI 設定。確保所有 pipeline 結構一致。
  2. ② DSL2 Modules (Reusable)：每個 tool (e.g., FASTQC, BWA, STAR) 都是獨立 module，可在多個 pipeline 重用。2026 共有 1,200+ modules 在 nf-core/modules repo。新 pipeline 只需「組裝樂高」。
  3. ③ nf-core lint：自動檢查 30+ 規範：版本號、CHANGELOG、conda yaml、docker image、test config、必要 metadata。未通過 lint 無法上 PR review。
  4. ④ GitHub Actions Matrix CI：每 PR 觸發在 Ubuntu / macOS 上跑 mini 測試資料集，分別用 Conda / Docker / Singularity 三種容器。失敗就阻擋 merge。
  5. ⑤ Bot 自動化：nf-core-bot 自動標 issue、自動關 stale PR、自動 release tag、自動推 Zenodo DOI——大幅減少 maintainer 負擔。
  6. ⑥ Schema-driven UI：nextflow_schema.json 描述所有參數，自動產生 Web UI、CLI help、文件——一份來源、多處輸出（single source of truth）。
  7. ⑦ Test Data Hub：nf-core/test-datasets repo 集中所有 pipeline 用的小型測試資料（每檔 <100 MB），保證 CI 跑得動。
  8. ⑧ Slack + 月度 hackathon：3000+ 人 Slack 即時溝通；每月有跨機構 hackathon。社群治理跟程式碼一樣重要。
  9. ⑨ Code of Conduct + 領導小組：避免大型專案常見的 toxic 風氣與 BDFL 偏差。Phil Ewels 領頭但有 4 人 Core Team 投票決策。

對比典型學術 pipeline：研究生寫一個 shell script 串十個工具，畢業後沒人維護——版本固定 2020、依賴失效、README 過時。nf-core 把這種「拋棄式 pipeline」轉成「可持續基礎設施」。

更深的啟示：nf-core 證明軟體工程不只是技術，更是社群治理。同樣的觀念也適用於 Bioconductor（每 6 個月 release + R CMD check）、scverse（multi-language interop）、Galaxy Training Network（200+ 教材的同行審查）。2026 一個 bioinformatics 研究團隊的「軟體成熟度」高低，已成為審查與資助的關鍵指標。

nf-core (Ewels et al. 2020 Nature Biotechnology) is bioinformatics' most successful open-source governance case — 3,000+ contributors, 100+ certified pipelines, used in thousands of papers. Let's dissect how it engineered all this:

  1. ① Cookiecutter template: one command, nf-core create, scaffolds a full pipeline — main.nf, modules, subworkflows, tests, docs, CI configs. Ensures structural consistency across pipelines.
  2. ② DSL2 Modules (Reusable): each tool (FASTQC, BWA, STAR, …) is an independent module reusable across pipelines. By 2026, 1,200+ modules live in nf-core/modules. New pipelines just "assemble Lego."
  3. ③ nf-core lint: auto-checks 30+ standards: version numbers, CHANGELOG, conda yaml, docker image, test configs, required metadata. Failing lint blocks PR review.
  4. ④ GitHub Actions Matrix CI: every PR runs mini test datasets on Ubuntu / macOS with Conda / Docker / Singularity. Failure blocks merge.
  5. ⑤ Bot automation: nf-core-bot auto-labels issues, closes stale PRs, tags releases, pushes Zenodo DOIs — slashes maintainer load.
  6. ⑥ Schema-driven UI: nextflow_schema.json describes all parameters; the Web UI, CLI help, and docs auto-generate from it — one source of truth, multiple outputs.
  7. ⑦ Test Data Hub: nf-core/test-datasets centralizes tiny test data (<100 MB each) so CI stays fast.
  8. ⑧ Slack + monthly hackathons: 3,000+ on Slack for real-time talk; monthly cross-institution hackathons. Community governance matters as much as code.
  9. ⑨ Code of Conduct + leadership team: avoids the toxic culture and BDFL pitfalls of large projects. Phil Ewels leads, but a 4-person Core Team votes.

Contrast with typical academic pipelines: a grad student writes a shell script chaining 10 tools, graduates, and nobody maintains it — version pinned to 2020, deps broken, README stale. nf-core turns "throwaway pipelines" into "sustainable infrastructure."

Deeper takeaway: nf-core proves that software engineering is not just tech — it's community governance. The same idea drives Bioconductor (6-month release + R CMD check), scverse (multi-language interop), Galaxy Training Network (peer-reviewed 200+ tutorials). By 2026, a bioinformatics group's "software maturity" has become a key criterion for grant review and journal acceptance.

常見誤解

九、常見誤解

❌ 「Agile = 不寫文件」

Agile Manifesto 寫的是「working software over comprehensive documentation」——是 「重視」working software 「優於」過度文件，不是「不要文件」。Agile 仍需要 user story、acceptance criteria、API docs、README。沒文件的 Agile 是混亂，不是敏捷。

The Agile Manifesto says "working software over comprehensive documentation" — "valuing" working software "over" excessive docs, not "no docs." Agile still needs user stories, acceptance criteria, API docs, READMEs. No-docs Agile is chaos, not agility.

❌ 「TDD 浪費時間」

研究 (Bissi 2016 metaanalysis) 顯示 TDD 前期增加 15-35% 開發時間，但 bug 減少 40-90%。整體 maintainence 成本下降。bioinformatics 對「正確性」要求極高（一個比對 bug 影響百篇論文），TDD ROI 特別高。

Studies (Bissi 2016 meta-analysis) show TDD adds 15-35% upfront development time but reduces bugs by 40-90%. Total maintenance cost drops. Bioinformatics is correctness-critical (one alignment bug can affect 100+ papers) — TDD ROI is especially high.

❌ 「CI/CD 只用於 web」

Bioinformatics 完全可用！nf-core 100+ pipeline 都跑 GitHub Actions CI；Bioconductor 每天對 2,200 套件跑 R CMD check；Galaxy Training Network 自動測 200+ tutorials。2026 沒有 CI 的論文程式碼，難以被信任。

Bioinformatics uses it everywhere! nf-core runs 100+ pipelines on GitHub Actions; Bioconductor runs R CMD check on 2,200 packages daily; Galaxy Training Network auto-tests 200+ tutorials. By 2026, paper code without CI is hard to trust.

❌ 「Git push --force 沒問題」

對 public branch 用 --force 是團隊大忌。會改寫他人 commit、丟失他人工作。安全版本：--force-with-lease——只在「沒有他人更新」時才允許。已被 force push 的 commit 仍可用 git reflog 找回（90 天內）。

Force-pushing public branches is team poison — rewrites others' commits, loses their work. Safer: --force-with-lease — only allowed when nobody else has pushed. Lost commits can still be recovered via git reflog (within 90 days).

SOLID 五原則展開

九-A、SOLID 五原則細節

SOLID 是 Robert C. Martin (Uncle Bob) 2000 年濃縮 50 年 OOP 經驗的五條規則。許多人背得出來，但少有人能正確應用。

SOLID is Robert C. Martin (Uncle Bob)'s 2000 distillation of 50 years of OOP experience. Many can recite them; few apply them correctly.

S — Single Responsibility

「一個類別只有一個改變的理由」。違反範例：User class 同時負責驗證密碼、發 email、寫 DB——任一需求變動都要改它。改善：拆 UserValidator、EmailService、UserRepository。
生資對應：別把 「parse BAM」、「計算覆蓋率」、「畫圖」 寫在同一個 Python 類別裡。

"A class should have only one reason to change." Anti-example: a User class that handles password validation, email sending, and DB writes — any of those evolving forces edits. Fix: split into UserValidator, EmailService, UserRepository.
Bio: don't put "parse BAM," "compute coverage," and "plot" in one Python class.

O — Open/Closed

「對擴充開放、對修改封閉」。新增功能應該不修改既有程式碼，而是加新類別/外掛。如 Aligner 介面 + BWAAligner / BowtieAligner / STARAligner——新增 minimap2 不需動既有 code，只加 Minimap2Aligner。生資對應：Snakemake 的 rule、Nextflow 的 process 都符合此原則。

"Open to extension, closed to modification." New behavior should arrive as a new class/plugin, not as edits to existing code. E.g., Aligner interface + BWAAligner / BowtieAligner / STARAligner — adding minimap2 means a new Minimap2Aligner, not edits elsewhere. Bio: Snakemake rules and Nextflow processes embody this.

L — Liskov Substitution

子類必須能完全替代父類。Barbara Liskov 1987 提出，1994 被 Martin 列入 SOLID。違反範例：Penguin extends Bird 但 penguin.fly() 不能跑——應該重新設計 hierarchy。正方形繼承長方形是經典 LSP 違反範例。
生資對應：RNAseqAligner extends DNAAligner 若強制要 splice junction 處理，反而破壞 DNA 版的呼叫端。

Subclasses must be substitutable for their parents. Barbara Liskov 1987 (Martin added it to SOLID in 1994). Anti-example: Penguin extends Bird but penguin.fly() can't run — redesign the hierarchy. Square inheriting from Rectangle is the classic LSP violation.
Bio: RNAseqAligner extends DNAAligner that forces splice-junction handling can break callers expecting DNA semantics.

I — Interface Segregation

客戶端不應被迫依賴它不用的方法——介面要小而專。違反範例：一個 BioFile interface 同時定義 readFastq()、readBam()、readVcf()——FASTQ-only 的 class 也被迫實作另外兩個。改善：拆 FastqReader、BamReader、VcfReader 三個 interface。Bioconductor 的 S4 class hierarchy 多元繼承就遵守此原則。

Clients shouldn't depend on methods they don't use — keep interfaces small and focused. Anti-example: a BioFile interface declaring readFastq(), readBam(), readVcf() — a FASTQ-only class is forced to implement the others. Fix: split into FastqReader, BamReader, VcfReader. Bioconductor's S4 multi-inheritance follows this principle.

D — Dependency Inversion

高層模組不該依賴低層，兩者都依賴抽象。具體寫法：依賴注入 (DI)。例：你的 variant caller 邏輯不該硬編 open("input.bam")——而是接收一個 BamReader 物件當參數。測試時可注入 mock。生資對應：Snakemake 的 input/output 路徑都是參數而非硬編；nf-core 的 channel 也是 DI 的實踐。

High-level modules shouldn't depend on low-level ones; both depend on abstractions. Concretely: dependency injection (DI). Don't hardcode open("input.bam") in your variant caller — receive a BamReader as a parameter. Tests can inject mocks. Bio: Snakemake's parameterized input/output paths and nf-core's channels are DI in practice.

Clean / Hexagonal / Onion 架構

九-B、Clean / Hexagonal / Onion 架構

2010 之後 enterprise software 流行「分層架構」三大流派——本質都是 SOLID 的進階形：

Post-2010, three "layered architecture" schools dominate enterprise software — all advanced forms of SOLID:

① Hexagonal (2005, Cockburn)

Alistair Cockburn 提出「ports & adapters」：核心商業邏輯放中央，port 是抽象介面，adapter 連接外界（DB、UI、API、檔案）。換 DB 從 MySQL 到 PostgreSQL 只改 adapter，核心不動。生資對應：Snakemake / Nextflow 把 「規則邏輯」 與 「實際 IO」 分離，正是 hexagonal 精神。

Alistair Cockburn's "ports & adapters": business logic at the core; ports are abstract interfaces; adapters connect the outside world (DB, UI, API, files). Switching MySQL→PostgreSQL only changes the adapter; the core is untouched. Bio: Snakemake/Nextflow separating "rule logic" from "actual IO" is hexagonal in spirit.

② Onion (2008, Palermo)

Jeffrey Palermo 的「洋蔥架構」：最內層是 domain entity（純資料）、外層 domain service、再外 application、最外 infrastructure。依賴只能由外往內，內核完全不知道 framework 存在。優：testability 極高；缺：boilerplate 多。

Jeffrey Palermo's "Onion": innermost = domain entities (pure data), then domain services, then application, then infrastructure. Dependencies only point inward; the core has no idea a framework exists. Pro: extreme testability. Con: heavy boilerplate.

③ Clean (2017, Martin)

Uncle Bob 在 Clean Architecture 一書中綜合 hexagonal + onion，提出四個同心圓：Entities → Use Cases → Interface Adapters → Frameworks & Drivers。Dependency Rule：依賴只能向內。Spring Boot、ASP.NET Core、Phoenix Framework 的「典範 codebase」多採用。

Uncle Bob's Clean Architecture book combines hexagonal + onion into four concentric rings: Entities → Use Cases → Interface Adapters → Frameworks & Drivers. Dependency Rule: dependencies point inward only. Many "exemplary codebases" for Spring Boot, ASP.NET Core, Phoenix Framework adopt it.

Twelve-Factor App

九-C、Twelve-Factor App

2011 年 Heroku 共同創辦人 Adam Wiggins 發表 12factor.net，定義雲端原生 SaaS 應用該遵守的 12 條：

  1. Codebase：一個 codebase 對應多個 deploy（Git 倉庫 single source of truth）。
  2. Dependencies：明確宣告（requirements.txt / package.json），不依賴系統內建。
  3. Config：環境變數注入；絕不把 DB 密碼 commit 進 Git。
  4. Backing services：DB、cache、queue 都當作 attached resource，可隨時換。
  5. Build, release, run：三階段明確分離；release 不可變。
  6. Processes：stateless；session 放外部（Redis / DB）。
  7. Port binding：應用自帶 web server，不依賴 Apache/Nginx。
  8. Concurrency：用 process model 水平擴展，而非 thread。
  9. Disposability：fast startup & graceful shutdown，方便彈性擴縮。
  10. Dev/prod parity：開發、staging、production 環境差異最小。
  11. Logs：當成事件 stream 寫到 stdout；不要寫檔案。
  12. Admin processes：管理任務（DB migration、報表）跟主程式一起 release。

對生資 pipeline 的啟示：① 把 reference genome 路徑、線程數、記憶體設定全當 env var，不寫死 ② 用 environment.yml 或 requirements.txt 鎖版本 ③ Snakemake / Nextflow 的 process 應該 stateless，可重跑 ④ log 寫 stdout 讓 cluster scheduler 收集——這 4 點就是「Twelve-Factor for Bioinformatics」。

2011 — Heroku co-founder Adam Wiggins published 12factor.net, defining 12 rules for cloud-native SaaS:

  1. Codebase: one codebase, many deploys (Git as single source of truth).
  2. Dependencies: explicit (requirements.txt / package.json), no implicit system packages.
  3. Config: env vars; never commit DB passwords to Git.
  4. Backing services: DB, cache, queue as attached resources, swappable.
  5. Build, release, run: cleanly separated; releases are immutable.
  6. Processes: stateless; session in external store (Redis/DB).
  7. Port binding: app ships its own web server; no Apache/Nginx dependency.
  8. Concurrency: scale out via process model, not threads.
  9. Disposability: fast startup & graceful shutdown for elastic scaling.
  10. Dev/prod parity: minimize differences between dev, staging, prod.
  11. Logs: event streams to stdout; never write to files.
  12. Admin processes: management tasks (DB migration, reports) ship with the main app.

Bioinformatics implications: (1) genome path, thread count, memory all as env vars, not hardcoded; (2) lock versions in environment.yml / requirements.txt; (3) Snakemake/Nextflow processes stateless and re-runnable; (4) log to stdout so cluster schedulers collect them — that's "Twelve-Factor for Bioinformatics" in four points.

可觀測性三柱

九-D、可觀測性三柱

2017 後 SRE 圈普遍採用 「三柱」 框架：

Since 2017 the SRE community has adopted a "three-pillars" framework:

① Metrics 指標

數值型時序資料：CPU 使用率、HTTP latency、queue 長度。Prometheus + Grafana 是事實標準。四個黃金訊號 (Four Golden Signals)：Latency、Traffic、Errors、Saturation。生資對應：cluster job 的 CPU/RAM/IO 監控、Snakemake/Nextflow 的 trace 報告。

Numeric time-series: CPU usage, HTTP latency, queue depth. Prometheus + Grafana is the standard. Four Golden Signals: Latency, Traffic, Errors, Saturation. Bio: cluster job CPU/RAM/IO monitoring, Snakemake/Nextflow trace reports.

② Logs 日誌

離散事件文字記錄。結構化 (JSON) log 比 plain text 好搜尋。ELK (Elasticsearch + Logstash + Kibana)、Loki + Grafana、Datadog 都是主流。生資對應：BWA / GATK / Snakemake 的 stderr log；務必加 timestamp 與 step name。

Discrete textual events. Structured (JSON) logs beat plain text for search. ELK (Elasticsearch + Logstash + Kibana), Loki + Grafana, Datadog dominate. Bio: BWA / GATK / Snakemake stderr logs — always add timestamps and step names.

③ Traces 追蹤

分散式請求在多個微服務間的完整路徑。OpenTelemetry (2019 CNCF) 是現代標準，Jaeger / Zipkin / Tempo 是 backend。一個 HTTP request 變成 200 條 span 在不同 service 間流動。生資對應：multi-step pipeline 的 DAG trace（每個 rule 的 start/end time），Nextflow 的 trace.txt + report.html。

End-to-end path of a distributed request through services. OpenTelemetry (2019 CNCF) is the standard; Jaeger / Zipkin / Tempo are backends. One HTTP request fans out into 200 spans across services. Bio: multi-step pipeline DAG traces (start/end per rule); Nextflow's trace.txt + report.html.

SRE 三大關鍵指標：
① SLI (Service Level Indicator)：實際測量值（例：99% 請求 < 200ms）。
② SLO (Service Level Objective)：目標（例：99.9% uptime）。
③ Error Budget：1 − SLO（例：0.1% 失敗額度），用光就要凍結 feature release。

SRE's three key metrics:
(1) SLI (Service Level Indicator): actual measurement (e.g., 99% requests < 200ms).
(2) SLO (Service Level Objective): target (e.g., 99.9% uptime).
(3) Error Budget: 1 − SLO (e.g., 0.1% failure quota); burn it and feature releases freeze.
From Google SRE Book (2016); now the lingua franca at Netflix, AWS, Meta, Stripe.
Conway's Law & DDD

九-E、Conway 定律與 DDD

Conway 定律 (1967)：「系統的架構，會反映設計它的組織的溝通結構。」
即：3 個團隊做的 compiler 一定有 3 個 pass；2 個團隊做的網站，前後端就會分離。Netflix、Spotify、Meta 都刻意把組織拆成「逆 Conway 操作」——先設計理想架構，再依此組織團隊。

對生資的啟示：① 若同一論文有 wet lab + dry lab，pipeline 介面常會反映兩方溝通 ② Bioconductor 套件之間的依賴 = R 套件作者社群的合作網絡；③ nf-core 之所以模組化得這麼好，是因為它先有跨機構社群，才有 pipeline 標準。

Domain-Driven Design (DDD, Eric Evans 2003)：複雜業務系統的設計法。核心觀念：

  • Ubiquitous Language：開發者跟領域專家用同一套詞彙。如生資的「peak」、「motif」、「splice junction」要在程式碼中與生物學家認知一致，不要叫 x1。
  • Bounded Context：每個子領域有自己的模型。「Sample」 在 wet-lab 是 「tube」，在 LIMS 是 「accession ID」，在 RNA-seq pipeline 是 「FASTQ pair」——三個 bounded context。
  • Aggregate Root：複雜物件的唯一入口。如 Experiment 是 root，包含多個 Sample、Library、SequencingRun。
  • Event Sourcing：不存 state，存 event 序列。生資 ELN (Electronic Lab Notebook) 適用此模式。

DDD 看似抽象，但 對於設計 LIMS、ELN、複雜 multi-omics 平台不可或缺。Benchling、LabKey、SciNote 都受 DDD 啟發。

Conway's Law (1967): "The architecture of a system mirrors the communication structure of the organization that built it."
A 3-team compiler ends up with 3 passes; a 2-team website ends up front-end/back-end split. Netflix, Spotify, Meta intentionally apply "inverse Conway" — design the ideal architecture first, then organize teams around it.

Bioinformatics implications: (1) wet-lab + dry-lab papers have pipeline interfaces that mirror cross-team communication; (2) Bioconductor inter-package dependencies = the R-package author community's collaboration network; (3) nf-core is so modular because the cross-institutional community came first, then the pipeline standard.

Domain-Driven Design (DDD, Eric Evans 2003) — design for complex business systems. Core ideas:

  • Ubiquitous Language: developers and domain experts share vocabulary. In bio, "peak," "motif," "splice junction" must match biologist usage — don't name them x1.
  • Bounded Context: each subdomain has its own model. "Sample" = tube in wet lab, accession ID in LIMS, FASTQ pair in RNA-seq pipeline — three bounded contexts.
  • Aggregate Root: unique entry to a complex object. Experiment as root contains many Sample, Library, SequencingRun.
  • Event Sourcing: store events, not state. Great fit for ELN (Electronic Lab Notebook).

DDD looks abstract but is essential for designing LIMS, ELN, and complex multi-omics platforms. Benchling, LabKey, SciNote are all DDD-inspired.

💭 延伸思考

十、延伸思考

  1. LLM (Copilot / Claude Code / Cursor) 改寫了軟體工程的什麼？程式碼生成速度提高 3-10×，但 code review、架構設計、debug、測試的負擔反而增加。「Vibe coding」是真的趨勢嗎？還是只是初期生產力提升、長期維護災難？2025 GitHub 調查顯示 41% 開發者「審 AI 程式比寫還累」。
  2. What did LLMs (Copilot / Claude Code / Cursor) rewrite about software engineering? Code generation is 3-10× faster, but code review, architecture, debugging, and testing get heavier. Is "vibe coding" a real trend? Or short-term productivity, long-term disaster? GitHub's 2025 survey: 41% of devs say "reviewing AI code is harder than writing it."
  3. 為何 bioinformatics 的可重現性比一般 SE 更難？① 資料量大（TB-PB）難以 commit；② 工具版本即使一個小數點都會改變結果；③ 隨機種子未固定；④ Cluster 環境異質；⑤ 演算法本身有隨機性。FAIR + 容器化 + workflow 三劍客是目前最佳解，但仍遠不夠。
  4. Why is reproducibility harder in bioinformatics than typical SE? (1) Massive data (TB-PB) hard to commit; (2) tool version differences alter results; (3) random seeds not pinned; (4) heterogeneous clusters; (5) inherent algorithmic randomness. FAIR + containers + workflow are the best current answer, but far from sufficient.
  5. Crowdstrike 2024 之後，kernel-mode 軟體應該如何設計？EU 與美國立法要求 staged rollout、強制 sandboxing、kernel API 限制。微軟 2025 開始限制 EDR 廠商存取 kernel。這是否會降低安全產品的有效性？還是它本來就不該寫在 kernel？
  6. After Crowdstrike 2024, how should kernel-mode software be designed? EU and US laws now mandate staged rollouts, sandboxing, kernel-API limits. Microsoft from 2025 restricts EDR vendors' kernel access. Does this weaken security products? Or were they never supposed to live in the kernel anyway?
