軟體工程

寫程式 ≠ 寫軟體。軟體工程是「在有限資源下，交付能維運的系統」。本章帶你看 SDLC、Git、測試、CI/CD 與 2026 主流實踐。

Programming is not engineering. Software engineering is "delivering maintainable systems under finite resources." This chapter walks through SDLC, Git, testing, CI/CD, and 2026 best practices.

概覽

寫程式 vs 寫軟體

「能跑」的程式很容易；「能跑五年、十個工程師可以接手、每週可安全部署」的軟體很難。軟體工程處理規模、變化、團隊與時間維度下的挑戰：需求變動、人員流失、技術債、安全漏洞、效能瓶頸。

Google 把軟體工程定義為「programming integrated over time」——程式設計加上時間維度的積分。

"It runs" is easy; "runs for five years, hand-off-able to ten engineers, safely deployable every week" is hard. Software engineering tackles scale, change, team, and time: shifting requirements, churn, tech debt, security holes, perf bottlenecks.

Google defines software engineering as "programming integrated over time" — programming plus the time dimension.

💡
核心觀念：軟體成本中「寫程式」只佔 20%，其餘 80% 是維護——找 bug、重構、回應需求變動。所以「可讀性、可測試性、可維運性」遠重於「炫技」。 Core idea: Only ~20% of software cost is writing code; ~80% is maintenance — fixing bugs, refactoring, responding to changes. Readability, testability, and operability beat cleverness.
SDLC 六階段

一、SDLC 六階段

Requirements

蒐集需求、定義使用者故事、寫驗收條件。錯誤的需求是專案失敗的頭號原因。

Gather needs, write user stories, define acceptance criteria. Wrong requirements are the #1 cause of project failure.

Design

系統架構、API 介面、資料模型、技術選型。產出 design doc / RFC 並做設計審查。

System architecture, API surfaces, data model, tech choices. Produce design docs / RFCs and review them.

Implementation

真正寫程式碼。配合 code review、linter、formatter 維持品質。

Actually write code. Use code review, linters, formatters to keep quality.

Testing

單元測試、整合測試、E2E 測試、效能測試、安全測試。CI 自動跑。

Unit, integration, E2E, performance, and security tests — all automated in CI.

Deployment

容器化、CD 流水線、藍綠 / 金絲雀部署，配合可觀測性 (logs / metrics / traces)。

Containerize, run a CD pipeline, blue-green / canary release with full observability (logs / metrics / traces).

Maintenance

監控 SLA、修 bug、處理事故、重構、退役舊系統——也是工程師花最多時間的階段。

Monitor SLAs, fix bugs, run incidents, refactor, decommission old systems — where engineers spend the most time.

Git 與分支

三、Git 與分支模型

Git (Linus Torvalds, 2005) 是當今絕對主流的版本控制系統。每個 commit 都有 SHA-1 hash，Repo 是一張 commit DAG（有向無環圖）。

核心概念：commit（快照）、branch（分支指標）、merge（合併，保留歷史）、rebase（線性化歷史，但會改寫 SHA）、pull request / merge request（review 流程）。

Git (Linus Torvalds, 2005) dominates today's version control. Each commit is a SHA-1 hash; a repo is a DAG of commits.

Core terms: commit (snapshot), branch (a moving pointer), merge (preserves history), rebase (linearizes history, rewrites SHAs), pull request / merge request (review workflow).

GitHub Flow (simplified)
main  ● ──── ● ──── ● ──────── ● ──── ● ────► production
                \\ ────────── ↗ [merge PR]
feature            ● ── ● ── ●
↑ 每個 feature 都從 main 分支出，做完開 PR 合回。Each feature branches off main; open a PR to merge back.
測試金字塔

四、測試金字塔

🧪 Unit Test (底層)

測試單一函式 / 類別。快、多、穩定。占整體測試的 70%。用 pytest / Jest / JUnit。

Test a single function/class. Fast, many, stable. ~70% of all tests. Tools: pytest, Jest, JUnit.

🔌 Integration Test

測試多個模組互動，例如 API + DB。約占 20%，較慢但比 E2E 穩定。

Test multiple modules together (e.g. API + DB). ~20%; slower than units but more stable than E2E.

🌐 E2E (頂端)

模擬使用者實際操作整個系統，例如 Selenium / Playwright / Cypress。慢、少、易碎，僅占 10%。

Simulate real user flows end to end (Selenium / Playwright / Cypress). Slow, few, flaky — ~10%.

TDD（測試驅動開發）：① 先寫一個會失敗的測試 → ② 寫剛好能通過的程式 → ③ 重構。Red → Green → Refactor 循環。

TDD (Test-Driven Development): (1) write a failing test → (2) write just enough code to pass → (3) refactor. The Red → Green → Refactor cycle.

CI/CD、SOLID、文件

五、CI/CD 與程式品質

CI (Continuous Integration)：每次 push 自動跑測試 + lint + build。GitHub Actions、GitLab CI、Jenkins、CircleCI 是主流工具。

CD (Continuous Delivery / Deployment)：通過所有檢查後自動部署到 staging / production。2026 業界目標：commit → production < 30 分鐘。

SOLID 原則（OOP 設計五大原則）：

  • Single Responsibility — 一個類別只做一件事
  • Open/Closed — 對擴展開放，對修改封閉
  • Liskov Substitution — 子類能完全替代父類
  • Interface Segregation — 介面分離，別塞太大
  • Dependency Inversion — 依賴抽象、不依賴具體

文件化：README、docstring、ADR (Architecture Decision Record)、API 規格 (OpenAPI / Swagger / GraphQL schema)。「程式碼說 how，文件說 why」。

CI (Continuous Integration): on every push, run tests + lint + build automatically. GitHub Actions, GitLab CI, Jenkins, CircleCI are common.

CD (Continuous Delivery / Deployment): auto-deploy to staging / production once checks pass. 2026 target: commit → production in under 30 minutes.

SOLID — five OOP design principles:

  • Single Responsibility — one class, one reason to change
  • Open/Closed — open to extension, closed to modification
  • Liskov Substitution — subtypes replace base types cleanly
  • Interface Segregation — many small interfaces, not one fat one
  • Dependency Inversion — depend on abstractions, not concretions

Documentation: README, docstrings, ADRs (Architecture Decision Records), API specs (OpenAPI / Swagger / GraphQL schemas). "Code says how; docs say why."

Merge vs Rebase

六、Merge vs Rebase

🌳 Git 工作流選擇樹

Q1:
分支已 push 到遠端，多人協作？→ 是 → 用 merge，絕對不要 rebase 共享分支（會改寫歷史影響他人）。
Q2:
只是自己的 feature branch、想在 PR 前整理 commit？→ 是 → interactive rebase (git rebase -i) 可 squash / reorder commits，讓歷史乾淨。
Q3:
要把 main 的最新修改同步到 feature？→ rebase onto main 較常見（線性歷史）；或 git merge main 也行。
Q4:
TDD 還是先寫程式再測？→ 高風險邏輯、明確規格 → TDD；探索性 / prototype → 先寫程式再補測試，但 PR 前必須有測試。
Q1:
Branch already pushed and shared? → Yes → Use merge. Never rebase shared branches (rewriting history breaks teammates).
Q2:
Only your local feature branch, cleaning up before PR? → Yes → Interactive rebase (git rebase -i) to squash / reorder commits.
Q3:
Sync latest main into feature? → Rebase onto main is common (linear history); git merge main also works.
Q4:
TDD or code-first? → Risky logic, clear spec → TDD; exploratory / prototype → code first, but tests required before PR.

七、pytest 與 Git 工作流

# calc.py — 受測模組 / module under test
def add(a: int, b: int) -> int:
    return a + b

def divide(a: float, b: float) -> float:
    if b == 0:
        raise ValueError("divisor must not be zero")
    return a / b


# test_calc.py — pytest 測試 / pytest tests
import pytest
from calc import add, divide

def test_add_basic():
    assert add(2, 3) == 5

# 用 parametrize 一次測多組 / table-driven tests
@pytest.mark.parametrize("a, b, expected", [
    (10, 2, 5),
    (-6, 3, -2),
    (1, 4, 0.25),
])
def test_divide_cases(a, b, expected):
    assert divide(a, b) == expected

def test_divide_by_zero_raises():
    with pytest.raises(ValueError):
        divide(1, 0)

# 執行：pytest -v  /  Run with: pytest -v
// 典型 GitHub Flow / Typical GitHub Flow
git checkout main
git pull                          // 拉最新
git checkout -b feature/login    // 開新分支

// 寫程式 + 寫測試 / Code + tests
while work_remaining:
    edit files
    pytest                       // 在本地跑測試
    git add .
    git commit -m "feat: add login form"

git push origin feature/login
open Pull Request on GitHub
// → CI 跑測試、lint、build → 同事 review →
if approved and CI_green:
    squash and merge            // 合回 main
    CD pipeline → staging → production
